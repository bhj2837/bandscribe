## 1. 목표와 범위

### 1.1 하는 것
- **입력:** 로컬 오디오 파일이 1순위다(CD·구입 음원 권장). YouTube 링크는 **2026-09-30 사용자 결정으로 기본 켜짐**이다. 사용자가 아래 위험 고지(S0)를 받고 기본 켜기를 요청했고, 그 동의가 `data/config.toml` `[consent]`에 기록된다. `youtube.enabled=false`로 끌 수 있다.
- **출력:**
  - 기타 **파트(Line)마다 탭 트랙 1개**와 베이스 탭 1개.
  - 음표마다 신뢰도 4종: 피치, onset, 파트, 프렛.
  - 형식: `.gp5`, `.gp`(GP7), alphaTex, 파트별 MIDI(양자화판과 연주판), 선택으로 PDF·MusicXML.
- **자동 추정:**
  - 튜닝(오픈 튜닝 일부 포함), 카포, A4 미세 오프셋
  - 박자표(복합 박자 포함), 템포, 못갖춘마디, 셋잇단 느낌
  - 곡 편성(건반·신스 유무). 전사기 마스크를 정하는 데 쓴다.
  - 주법: 벤딩은 확정 표기, 나머지는 제안
  - 리듬 파트의 코드 이름
- **로컬 웹 UI:**
  - 원곡, 스템, 뷰, 탭 신스를 A/B로 비교해 듣는다.
  - 신뢰도를 색으로 보여 준다.
  - 키 1–2번으로 음표나 구절을 다른 파트로 옮기고, 옥타브와 줄을 고친다.
  - 모든 수정은 기록되어 보정 데이터가 된다.

### 1.2 안 하는 것 (v1)
- 드럼, 보컬, 건반은 채보하지 않는다. 판정 증거로만 쓴다.
- 깨끗한 파트별 스템을 결과물로 약속하지 않는다. 파트별 오디오는 연습용 부산물이다.
- 공유, 공개, 상업 사용은 하지 않는다.
- YouTube 쿠키나 PO 토큰은 따로 옵트인하지 않는 한 쓰지 않는다(S0 위험). YouTube 수집 자체는 2026-09-30 사용자 결정으로 기본 켜짐이다(끌 수 있다).
- Songsterr `/api/`를 자동으로 조회하지 않는다.
- 자체 lead/rhythm 분리기는 학습하지 않는다. 평가가 필요를 증명할 때만 M12에서 한다.

**결론:**
- 결과는 "고칠 곳이 표시된 좋은 초안"이다. 이 도구의 가치는 채보 시간과 수정 시간을 줄이는 데 있다. 이 가치는 **처음부터 채보하는 경우, 외부 AI 초안에서 고치는 경우와 비교해** 잰다(8.4, M4a).
- 밴드 믹스는 위 수치보다 어렵다.
- 아래 시나리오별 기대치는 모두 **미검증**이다. M5–M8에서 실측값으로 바꾼다.

### 1.4 설계 원칙
1. **산출물은 탭이다.** 분리는 증거를 만드는 수단이다. 어느 파트가 음표를 소유하는지는 늦게, 음표 단위로 정한다 [wf2:CRITIC].
2. **측정 먼저.** 평가 하네스를 모델 선택 전(M1a)에 만든다. 컴포넌트 결정은 창 단위로 큰 합성·Tier B 세트에서 하고, 곡 수가 적은 Tier A는 end-to-end 점검과 편집 시간 측정에 쓴다(8.1). 모든 선택지는 실험 번호(E#)와 결정 규칙을 갖는다. SDR은 진단용으로만 쓴다. **정답은 평가 대상 컴포넌트로 만들지 않는다**(8.3).
3. **약한 증거를 모아 마지막에 한 번 판정한다.** 뷰 × 전사기 × 반복 구간이 투표한다. 음표는 삭제하지 않고 감점한다.
4. **창마다 가장 싸고 믿을 만한 단서를 쓴다.**
   - 넓은 믹스: 스테레오 coherence
   - 음색이 다를 때: 악기 클래스
   - 리프가 반복될 때: 반복
   - 항상: 기호 규칙
5. **수정은 제품의 일부다.** 불확실한 10–30 %를 빨리 고치게 하고, 수정 로그로 보정한다.
6. **로컬 우선.** 백엔드는 교체할 수 있고, 모든 단계를 캐시하며, GPU에는 한 번에 모델 하나만 올린다. 클라우드는 옵트인 투표자다.
7. **법과 약관을 지킨다.** 로컬 파일이 1순위다. YouTube 경로는 2026-09-30 사용자 결정으로 기본 켜짐이지만 쿠키·PO 토큰은 끄고, 위험 고지와 동의 기록을 둔다. 결과는 비공개다. 라이선스가 불명확한 가중치는 재배포하지 않는다.

**단계 의존 (비순환):** 각 단계는 자기보다 앞 단계의 산출물만 읽는다. v1.1에 있던 역순 의존은 이렇게 풀었다.
- 보컬 활동과 드럼 기반 비트 2번째 가설은 S2가 아니라 S3.5에서 만든다. 스템이 필요하기 때문이다.
- S4의 클래스 토큰은 S3.5의 원시 전사(기타 스템 모노)에서 온다.
- S4의 반복 잔차 에너지는 S3.5가 솔로 게이트 없이 1차로 계산한다. S5는 S4의 솔로 게이트를 반영해 다시 계산한다.
- S7의 베이스 블리드 감점은 S3.5의 원시 베이스 음을 쓴다. S11은 S7의 기타 음을 쓴다. S11의 결과는 S7로 돌아가지 않는다.
- 베이스 근음과 리듬 코드의 교차 확인은 S14에서, 베이스와 기타의 공동 다운튠 선택은 S13에서 한다.
- DAG 실행기는 시작할 때 순환이 없는지 검사한다(9.7).

**실행 원칙:**
- GPU 단계는 한 번에 하나씩, 별도 프로세스로 돌린다.
- CPU 단계는 입력이 준비되는 대로 돌린다.
- MuScriptor는 패스 1(S3.5)과 패스 2(S6)에서 두 번 로드된다. 그 사이에 CenterWide(S5)가 GPU를 쓰기 때문이다. 로드 비용은 M2에서 잰다(미검증).

**프로필별 예상 시간 (4분 곡, 모두 추정·미검증):**
- `fast`: 분리 + 스템 전사 + 합친 트랙. S3.5는 믹스 전사를 건너뛰고 스템 에너지와 힌트로 편성을 정한다. 6–10분.
- `quality`: 로컬 경로 전부. S3.5의 MuScriptor 약 2패스(믹스 전체 편성, piano+other)가 더해진다. 15–30분이었던 v1.1 추정에 이 추가분은 아직 반영하지 않았다.
- `max`: 정제 루프, 추가 투표자, 클라우드를 더함. 60분 이하.

## 3. 단계별 상세

### 3.0 추가 요소 분류 [안1]

**기본 포함**
- 뷰 여러 개 전사. 창 단위 스테레오 특징이 A·P·트윈 리드에서 유일한 실제 단서였다 [실험:router_exp.py]. **음표별 스테레오 서명**은 그 연장이며, E22에서 검증할 가설이다(router_exp는 창 단위 특징만 쟀다).
- Basic Pitch 보조 투표(최소 음 길이를 낮춘 설정)와 벤딩 곡선.
- 반복 합의.
- 베이스 3-트래커 옥타브 앵커.
- float 디코드, A4 varispeed.
- S3.5 편성 추정.
- 솔로 게이트 **규칙판**: 보컬 비활동 + 경로별 리드 에너지 + 반복 잔차.

### S0 입력·정규화 (M0)

- **입력:** 로컬 파일(FLAC, WAV, MP3, M4A, OGG, Opus, WebM). YouTube URL(2026-09-30 사용자 결정으로 기본 켜짐, `youtube.enabled=false`면 거부).
- **출력:** `jobs/<song_key>/input/` 폴더.
  - 원본 컨테이너. 재인코딩하지 않는다.
  - `mix_44k_f32.wav`: 스테레오 float32, soxr로 재샘플.
  - `tuning.json`, (필요시) `mix_tuned.wav`.
  - `meta.json`: 출처, format_id/abr, 제목·앨범·길이·챕터·live_status, LUFS, true peak, 적용 게인, 플래그.
  - `song_key`는 `yt-<id>` 또는 `f-<PCM sha256 앞 16자>`다. 경로는 ASCII만 쓰고, 한글 제목은 meta.json 안에만 둔다.
- **1차 방법:**
  - **디코딩:** `ffmpeg -i IN -af aresample=44100:resampler=soxr -c:a pcm_f32le`.
    - **int16 디코드는 금지한다.** 크게 마스터링된 곡이 Opus로 +1.02 dBFS, AAC로 +1.58 dBFS 피크가 났다 [실험:codec_exp3.py].
    - 게인은 float 상태에서 true peak ≤ −1 dBFS가 되도록 주고, 게인 값을 저장한다.
  - **라우드니스 (E1):**
    - 상업 마스터의 중앙값은 −7.96 LUFS, musdb는 −16.02 LUFS다.
    - 큰 음량에서 분리기 SDR이 떨어지고(Demucs v3-B 10.11 → 9.26), 정규화로 대부분 회복된다(9.94). 단, 이 회복은 곡별 오라클 목표로 잰 값이다.
    - SW 설정은 `normalize: false`다. 그래서 −14/−16 LUFS 정규화를 E1로 시험한다.
  - **A4 오프셋:**
    - HPSS 화성 성분에 `librosa.estimate_tuning`을 쓴다. 반음 미만만 알 수 있다.
    - |c| > 15 cents(E16)이면 soxr로 2^(−c/1200)만큼 **재샘플(varispeed)**한다. 이후 단계는 이 파일을 쓴다.
    - 내보낼 때 시각만 되돌리고, 탭 헤더에 A = 440·2^(c/1200)을 적는다.
  - **플래그:**
    - 준모노(S/M < −30 dB): R0 경로로 보낸다.
    - ~16 kHz 컷오프: 이중 손실 압축.
    - DRC 스트림, 비표준 샘플레이트.
    - **다운믹스는 금지한다.**
  - **YouTube (2026-09-30 사용자 결정으로 기본 켜짐. 사용자가 아래 위험 고지를 받고 기본 켜기를 요청했고, 동의 문구는 `data/config.toml`의 `[consent] youtube`에 기록된다. 쿠키·PO 토큰은 계속 따로 끈다):**
    - `tools\yt-dlp.exe`를 **nightly** 채널로 쓴다. README가 일반 사용자에게 권하는 채널이다(stable은 2026.08.19).
    - `--js-runtimes node`를 쓴다. Node v24.10이 최소 요구(22)를 넘는다. 이 설정으로 yt-dlp가 YouTube의 JS 챌린지(signature, n 파라미터)를 푼다. 아래 위험 항목의 기술적 보호조치 문제는 **이 기본 경로에서 이미 생긴다.**
    - 명령: `-f "ba[format_id!*=drc][acodec=opus]/ba[format_id!*=drc]/ba" --write-info-json --sponsorblock-mark music_offtopic`
    - 재인코딩과 쿠키는 쓰지 않는다. 다운로드 사이에 5–10 s 쉰다. format_id를 기록한다.
- **대안 (yt-dlp 실패 시, 이 순서로):**
  1. `--update-to nightly` 후 재시도
  2. (옵트인, 추가 위험) bgutil PO-token 플러그인(GPL-3.0). exe에는 pip 플러그인이 붙지 않으므로 zip을 `yt-dlp-plugins\`에 넣는다.
  3. 로컬 파일 안내
  - 쿠키는 정지 위험을 고지한 뒤 명시적으로 옵트인할 때만 쓴다.
  - 141/774(Premium) 포맷은 범위 밖이다.
- **실행:** CPU, 수 초.
- **위험:**
  - 약관(한국어판, 2022-01-05 시행)은 허락 없는 다운로드와 자동 접근을 금지한다.
  - 저작권법 제30조 사적 복제에는, 불법 복제물임을 알고 한 복제는 제외된다는 판결이 있다(2008카합968).
  - **기술적 보호조치:** YouTube 경로 전체가, JS 챌린지를 푸는 기본 경로를 포함해, 해외 판례에서 기술적 보호조치 우회로 판단된 바 있다. 독일 함부르크 법원은 youtube-dl 호스팅 사건에서 YouTube의 'rolling cipher'를 유효한 기술적 보호조치로 봤다. 지방법원(LG) 판결은 2023-03 말, 고등법원(OLG) 항소 기각은 2024-11-27에 보도됐다 [재확인 2026-09-25, heise·TorrentFreak 보도 수준]. 리뷰가 제시한 사건번호(LG 310 O 316/21, OLG 5 U 54/23)는 확인하지 못했다(**미검증**). 한국 저작권법 제104조의2가 적용되는지는 **미검증**이고, 이 문서는 법률 자문이 아니다.
  - PO 토큰과 쿠키는 그 위에 얹히는 **추가 위험**이다(계정 정지, 추가 우회 해석). 그래서 YouTube를 켜도 따로 끈다.
  - 게스트 경로는 visionos 클라이언트 하나에 기댄다.
  - 코덱 영향이 작다는 결과는 합성 신호(실제 약 164 kbps)에서만 나왔다. E5에서 다시 잰다.
- **근거:** [gap:youtube-ingest] 검증, [실험:codec_exp.py].

### S1 버전·트리밍·힌트 (선택, M11)

- **출력:** meta.json에 다음을 추가한다: 선택한 버전(MV, 앨범, 라이브), 앞뒤 트림, 힌트(출처 포함).
- **버전 찾기:**
  1. Art Track(`Auto-generated by YouTube.`)인지 먼저 본다.
  2. 아니면 1순위로 ytmusicapi 1.12.3의 `search(filter='songs')`를 쓴다.
  3. 2순위로 `get_watch_playlist(videoId)['tracks'][i].get('counterpart')`를 본다. counterpart는 트랙 항목 안의 선택 키이고, 문서화된 방향은 노래→영상뿐이다. MV→앨범 방향은 **미검증**이다 [재확인 2026-09-25].
  - 두 버전을 길이와 함께 보여 준다. 스튜디오 곡은 앨범판이 기본이고, 라이브판은 바꾸지 않고 표시만 한다.
- **트리밍 우선순위:**
  1. 앨범판에 chroma DTW로 정렬
  2. SponsorBlock `music_offtopic`. 해시 버킷 응답을 **videoID로 거른다**.
  3. 스템 에너지
  - 앞뒤만 자른다. 곡 중간의 스킷은 마스킹해서 탭 시간과 영상 시간을 일치시킨다.
- **힌트:**
  - Songsterr는 **자동 조회하지 않는다.** robots.txt가 `/api/`를 막고, ai.txt는 사람을 대신해 제목·튜닝을 "보는 것"만 허용한다 [재확인 2026-09-25].
  - UI는 검색 페이지 링크만 준다. 파트 수, 파트 이름, 튜닝, 편성은 사용자가 입력한다.
  - 로컬 파일은 ffmpeg chromaprint(이 PC 빌드에 있음 [재확인 2026-09-25])와 AcoustID로 식별한다. 키는 사용자가 발급하고, 비상업 전용이며, 초당 3회 이하로 호출한다.
- **위험:**
  - MV와 앨범은 수 초 차이가 난다(Wonderwall 4:38 vs 4:19).
  - 커뮤니티 탭은 다른 버전일 수 있으므로 약한 사전 정보로만 쓴다.

### S2 전역 분석 (M1a–M3)

- **입력:** 전체 믹스만. 스템(S3)은 쓰지 않는다. 박자는 믹스 안의 드럼과 베이스가 싣는다.
- **출력:**
  - `grid.json`: 비트, 다운비트, 마디, 템포맵, 박자표, **비트 단위**(4분 / 점4분 / 8분), 못갖춘마디, 반/배 판정, 신뢰도.
  - `sections.json`
  - `repeat_map.json`: 마디 대응과 정렬 오프셋.
- **1차 방법:**
  - **비트:** Beat This! 1.1.0(MIT, final0, DBN 없음). GTZAN beat F1 89.1, downbeat 78.3(허용 ±70 ms).
  - **오디오 전달:** soundfile로 읽어 `Audio2Beats(signal, sr)`에 **메모리로** 넘긴다. torchaudio 2.9+ `load()`는 TorchCodec을 거치므로 shared FFmpeg가 필요하다. soundfile은 beat-this가 의존성으로 선언하지 않으므로 직접 설치한다.
  - **파생값:**
    - 템포 = 비트 간격
    - 박자표 = 구간별 마디당 비트 수의 최빈값
    - 첫 다운비트 앞 = 못갖춘마디
  - **복합 박자 판정:** Beat This!가 6/8·12/8에서 점4분음표와 8분음표 중 무엇을 비트로 잡는지는 곡마다 다를 수 있다 [리뷰, 미검증]. 그래서 마디 전반에서 비트 안 onset이 3분할에 몰리는지 본다. 3분할이 우세하면 6/8·12/8 가설(비트 단위 = 점4분음표)을 세운다. "4/4 + 셋잇단(또는 셋잇단 느낌)"과 가르지 못하면 두 가설을 모두 두고 UI 토글로 고른다(E14).
  - **반/배 검사:** onset 밀도와 비교한다. 템포 옥타브 오류가 남은 실패의 대부분이다(arXiv 2605.12287).
  - **비트 미세 보정:** 각 비트를 ±35 ms 안의 타악 onset에 맞춘다. 타악 onset은 전체 믹스의 HPSS 타악 성분에서 구한다. 드럼 스템은 S3 뒤라 쓰지 않는다.
  - **구간과 반복:** librosa 0.11로 비트 동기 CENS+MFCC 자기유사도, Laplacian 분할, lag 행렬.
- **대안:**
  - Beat This! small(CPU)
  - madmom DBN(git 빌드, 모델은 CC BY-NC-SA)
  - UI에서 다운비트 ±1 이동, 박자표·비트 단위 수정
  - all-in-one은 WSL에서만
- **위험:**
  - downbeat F1이 약 78 %다.
  - Klangio의 양자화 최고치(MUSTER 12.30)는 **정답 비트** 기준이다. 추정 비트에서의 성능은 측정된 적이 없다. 같은 표에서 별개 시스템인 "신경망 비트 추적"은 68.28이었다.
  - 루바토, 라이브.
  - **Beat This!는 정답 정렬에 쓰지 않는다.** 평가 대상이기 때문이다(8.3).
- **근거:** [gap:notation-output] 검증.

### S3 스템 분리 (M2)

- **출력:**
  - `{vocals,drums,bass,guitar,piano,other}.wav`: 스테레오 float32.
  - `nonvox` = mix − vocals − drums − bass.
  - `leftover` = mix − Σ stems. MSST `--extract_instrumental`은 스템 하나만 빼므로 직접 계산한다.
  - manifest: 모델 SHA256, 피크 VRAM(reserved·NVML 기준, 9.5).
- **1차 방법:**
  - **모델:** BS-RoFormer SW 6-stem(699 MB). guitar 9.01, piano 7.80, bass 14.62, drums 14.11.
  - **실행 도구:** ZFTurbo MSST(MIT, 커밋 고정)의 **모델 코드(`models/bs_roformer`)와 demix 함수만** 벤더링하고, 자체 추론 루프(약 100줄)를 쓴다 [안2].
    - MSST `requirements.txt`는 설치하지 않는다.
    - MSST `inference.py`를 그대로 쓰지 않는 이유: `inference.py`가 librosa, soundfile, tqdm과 `utils.audio_utils`를 import하고, `utils/audio_utils.py`는 모듈 최상단에서 `import matplotlib.pyplot as plt`를 한다 [재확인 2026-09-25]. `utils/settings.py`는 PyYAML을 쓴다 [리뷰].
    - 모델 코드의 최소 의존성: einops, rotary-embedding-torch, beartype, omegaconf, ml_collections, packaging(`attend.py`가 씀 [리뷰]). Mel-Band 계열을 쓰면 librosa(`from librosa import filters` [리뷰])도 필요하다.
    - 폴백: `inference.py`를 그대로 쓴다면 matplotlib, librosa, soundfile, tqdm, pyyaml, packaging을 추가한다.
  - **설정:** 업스트림 기본 dtype(fp32 가중치 + AMP), batch 1, num_overlap 2, chunk 588,800. SHA256을 고정한다.
- **부산물:** 기타 뺀 믹스와 베이스 뺀 믹스가 **연습용 반주**가 된다. M2부터 쓸 수 있다 [안2].
- **대안:**
  - python-audio-separator 0.47.0 이상. 이전 판은 드럼 스템이나 overlap이 틀린다.
  - **OOM 사다리:** 588,800 → 352,256 → 262,144 → CPU → (옵트인) MVSEP. 값은 모델 yaml의 STFT hop_length 배수로 맞춘다. hop이 512라면 588,800 = 512×1150이다. 배수가 꼭 필요한지는 **미검증**이다. 커뮤니티는 352,800으로 4 GB에서 돌렸다고 보고했다.
  - 라이선스가 걱정되면 xlance `gtr_mss`(MIT 태그, 8.60). 다만 SW에서 파인튜닝한 모델이다.
  - 빠른 기준선: htdemucs_6s(5.22).
- **실행:** GPU. 4분 곡에 2–6분 추정(**미검증**). Windows와 sm_75에서는 flash attention 대신 SDPA를 쓴다.
- **위험:**
  - **SW의 라이선스와 출처가 불명이다.** 원 계정이 삭제됐고, 점수가 Logic Pro 11.2와 일치한다. 개인용으로만 쓰고, 로컬 사본과 SHA256을 보관한다.
  - 분리 후 bin별 coherence와 ILD가 보존되는지는 **미검증**이다. 라우터의 전제이므로 M2에서 합성 A 믹스로 먼저 보고, M6에서 Tier B로 판정한다.
  - 디스토션 기타와 신스·오르간, 클린 기타와 일렉피아노가 서로 샌다.
- **근거:** [wf1:general-sota], [wf1:guitar-split] 검증.

### S3.5 스템 1차 분석: 편성 추정·원시 전사 (M2)

- **왜 필요한가:** MuScriptor의 `instruments`는 조건화와 동시에 **나머지 악기를 하드 마스크**한다. 편성을 빠뜨리면 건반·신스 음이 기타 클래스로 강제되고, 클린 기타를 빼면 그 기타가 사라진다. v1.1에는 "곡에 있는" 편성을 정하는 단계가 없었다. 또 S7의 블리드 감점에 필요한 piano/other 음표를 만드는 단계도 없었다.
- **입력:** 전체 믹스, S3 스템, S2 grid·반복 지도, 사용자 힌트(편성).
- **출력:**
  - `instrumentation.json`: 클래스별 존재 확률과 출처(전사, 스템 에너지, 힌트). UI에서 고칠 수 있다.
  - `raw/`: 원시 전사. 기타 스템 모노, 베이스 스템, piano+other.
  - 보컬 활동 곡선(보컬 스템 에너지, CPU).
  - (max) 드럼+베이스 스템으로 만든 비트 2번째 가설.
  - `repeat_resid_pass1`: 반복 잔차 1차.
- **방법:**
  1. 전체 믹스를 **전체 편성(모든 클래스)**으로 MuScriptor 1회 전사한다. 클래스별 활성도를 얻는다. 이 결과는 기준선 **B0**로도 쓴다(8.5).
  2. SW piano/other 스템의 구간별 에너지를 더한다. (선택) Mega-53 단일 스템 검출을 더한다.
  3. 사용자 힌트와 합쳐 클래스별 존재 확률을 낸다. 문턱 이상인 클래스만 S6 마스크 목록에 넣는다. 문턱은 E3에서 정한다(잠정).
     - **빠뜨리면 음이 사라지는 기타 클래스**(특히 클린)는 문턱을 낮게 둔다. 기타 스템에 에너지가 있으면 기타 3클래스는 모두 넣는 것을 시작값으로 한다.
  4. 원시 전사:
     - 기타 스템 모노: 기타 3클래스 + 추정 편성. 입력이 S6의 mono 뷰와 같으므로 캐시를 공유한다.
     - 베이스 스템: bass 클래스. S7의 베이스 블리드 감점에 쓴다. S11도 캐시를 공유한다.
     - piano+other 합: 건반·신스 클래스. S7의 블리드 감점에 쓴다.
  5. 반복 잔차 1차: S2 반복 지도로 기타 스템에서 구간 정렬 중앙값 차감을 **솔로 게이트 없이** 계산한다(CPU). 중앙값이 소수의 리드 출현에 강건하다는 가정에 기댄다(미검증). S4 솔로 게이트의 N 경로 에너지에 쓰고, S5가 게이트 결과를 반영해 다시 계산한다.
- **실행:** GPU(MuScriptor 약 2패스 추가: 믹스, piano+other) + CPU. 시간은 **미검증**이다. `fast` 프로필은 1번을 건너뛰고 스템 에너지와 힌트로만 편성을 정한다.
- **위험:**
  - 편성 오판이 하드 마스크로 번진다. 그래서 확률과 출처를 UI에 보여 주고, 사용자가 한 번에 고치게 한다.
  - 믹스 전사의 클래스 정확도는 공개되지 않았다.

### S4 기타 라우터 (M6)

- **입력:** 스테레오 기타 스템, grid·sections, S3.5 산출물(클래스 비율, 보컬 활동, 반복 잔차 1차), 피아노 스템.
- **출력:** 4마디 창(빠른 구간은 2마디)마다 다음을 담는다.
  - 특징값
  - R0–R3 확률과 여유
  - 클래스 비율
  - 솔로 게이트
  - 보컬 활동
- **특징:** STFT(n_fft 4096, hop 1024)로 계산한다.
  - S/M 에너지비
  - 에너지 가중 L/R coherence(~150 ms)와 coherence > 0.9인 에너지 비율
  - |ILD| < 3 dB 비율, > 15 dB 비율
  - coherent bin의 평균 |ILD|
  - 1–40 ms 지연 상호상관의 최댓값
- **시작 규칙:** 합성 신호에서 나온 값이다. M6에서 **분리된 스템** 기준으로 다시 맞춘다.

| 라벨 | 조건 | 합성 근거 |
|---|---|---|
| R0 좁음(B/F) | S/M < −12 dB 그리고 coherence > 0.95 | B −15~−19 dB / 0.98–1.00 |
| R1 ADT | 5–40 ms 지연 상호상관 > 0.5 | ADT 0.72, 진짜 더블 ≤0.22 |
| R2 넓은 같은 파트 더블(A) | coherence < 0.85, hard < 0.1, centre-ILD > 0.4 | A 0.69–0.78 |
| R3 다른 위치 다른 파트(P, 트윈) | coherent bin 평균 \|ILD\| > 6 dB, 또는 hard > 0.3 그리고 coherence < 0.6 | ±70 %에서 11.8 dB, 하드 L/R 0.82 |

- **핵심:** 판별 단서는 팬 인덱스가 아니라 **coherence**다. bin ILD는 리듬 더블 구간 에너지의 56 %를 '센터'로 오판한다.
- **솔로 게이트 (기본: 규칙판):**
  - 보컬 비활동: 약한 사전 정보.
  - 경로별 리드 에너지:
    - A: 곡 자체의 리듬만 있는 구간 대비 coherent 에너지 상승. 합성에서 0.18 → 0.42, 리드가 −6 dB면 0.23.
    - N: 반복 잔차 1차 에너지(S3.5).
- **솔로 게이트 (조건부, E9): MERT 솔로 분류기 이식판.**
  - 원래 모델은 HF `LongshenOu/guitar-solo-segment-cls-mjn`이다. guitar F1 87.5지만 라이브 2곡 기준이다.
  - **라이선스:** 코드(`Sonata165/LeadInstrumentDetection`)는 MIT다. 체크포인트 리포에는 **라이선스 태그가 없고**, 파일은 `segment_guitar_cls_mjn.ckpt` 하나(약 1.13 GB)다. 백본 MERT-v1-95M은 **CC BY-NC 4.0**이다 [재확인 2026-09-25, HF API]. 즉 "MIT 코드 + NC 백본 + 무표기 체크포인트"이고, 개인용으로만 쓴다.
  - **바로 끼울 수 없다.** README가 "being updated" 상태이고, Linux 환경이 Python 3.7·torch 1.12.1이다(macOS 환경은 Python 3.12·torch 2.3.0) [재확인 2026-09-25, README]. lightning 1.9.5, numpy 1.21.6, transformers 4.30.2, tensorflow 2.11 핀과 테스트 세트용 하드코딩 경로는 [리뷰]다. 체크포인트는 옵티마이저 상태가 든 Lightning 체크포인트로 보이며, torch 2.6+의 `weights_only` 기본값 때문에 피클된 hparams 로드가 실패할 수 있다 [리뷰].
  - **이식 절차 (M7b, E9 통과를 목표로):**
    1. 격리된 일회성 환경에서 `weights_only=False`로 state_dict만 추출한다. 신뢰하는 파일일 때만 한다.
    2. safetensors로 다시 저장한다.
    3. 분류 헤드를 다시 구현한다.
    4. MERT modeling 코드를 벤더링한다(gpu venv의 transformers 판과 무관하게).
    5. 입력 길이와 샘플레이트를 확인한다. MERT-v1 입력은 24 kHz다 [리뷰].
- **대안:** 애매한 창은 가능한 경로를 모두 돌리고 S8이 판정한다. 사용자가 구간별로 경로를 강제할 수 있다.
- **위험:**
  - 임계값이 합성 클립 하나에서 나왔다.
  - 리드에 딜레이·핑퐁·리버브가 걸리면 S로 샌다(합성 −16/−8.6 dB).
  - 쿼드 트래킹, 조용한 리드, 센터의 보컬·건반 블리드.
- **근거:** [wf2:CRITIC] gaps_resolved, [실험:router_exp.py], [wf2:spatial].

### S5 뷰 생성 (M6, M8)

- **출력:** `views/*.wav`. 모노 44.1 kHz이고 가설 태그가 붙는다. Basic Pitch와 MuScriptor가 입력을 모노로 다운믹스하므로 **뷰마다 별도 모노 파일**로 쓴다.
- **경로별 방법:**
  - **R2 (A):**
    - 기타 스템에 gilliaan/CenterWide-Models(HF 공개, 라이선스 태그 없음)를 돌려 centre를 뽑는다.
    - Mel-Roformer v3와 BS-Roformer v2 중 무엇을 쓸지는 E7에서 정한다. MDX23C는 작성자가 "원음에 없는 주파수를 만들 수 있다"고 경고했다.
    - **S = (L−R)/2는 리드가 없는 리듬 기준이다.** 드라이한 센터 모노 리드는 L−R에서 상쇄된다.
  - **R3 (P):** L, R을 쓴다. 부분 패닝이면 ADRess식 IPD/ILD 마스크를 쓴다.
  - **R1 (ADT):** 한 채널만 쓴다.
  - **R0 (N): 구간 정렬 반복 차감.**
    1. 같은 구간이면서 S4 솔로 게이트가 음성인 출현들을 비트 정렬한다. S3.5의 1차 잔차와 달리 게이트를 반영한다.
    2. 크기 스펙트로그램의 중앙값을 리듬 모델로 삼는다.
    3. 소프트 마스크로 리드 잔차를 뽑는다.
    - 합성에서 리드 SIR이 0 → 약 17 dB로 올랐고, 50 ms 오정렬에도 강건했다. REPET-SIM은 실패했다(−0.8~−1.8 dB) [실험:repet3.py].
  - **D/C:** 기본은 클래스 토큰으로 처리한다.
- **대안:**
  - IPD/ILD 마스크: 합성 약 6 dB, 오라클 15.3.
  - Bertom Phantom Center VST3(17.01, pedalboard로 호스팅).
  - **클라우드 (옵트인):**
    - MVSEP 101 두 단계 모델. 업체 발표 SDR 9.21이지만 세트는 비공개다. 무료 계정은 하루 50건, 10분 이하, MP3 출력.
    - Music.AI Guitar Parts: $0.10/분.
    - MVSEP 55/66/81.
  - **로컬 실험 투표자 (E17):** listra92 Mel-Band Roformer(337 MB), DryPaint HTDemucs(110 MB). 지표가 없고, 작성자 스스로 "very mediocre"라고 평했다.
- **위험:**
  - 센터 모델은 기타 스템에서 검증된 적이 없다.
  - 반복 차감은 리프가 리드 없이 다시 나올 때만 작동한다.
  - 더블 리듬 위의 트윈 리드는 채널마다 섞인다.

### S6 전사 (M2, M6)

- **출력:** `amt/<view>__<backend>.json`.
  - 음표: onset, offset, pitch, 악기 클래스, 뷰, 백엔드. MuScriptor는 velocity를 내지 않는다.
  - f0 트랙(보컬 스템, 리드 성향 뷰, 베이스 스템), Basic Pitch 음표별 벤딩.
- **1차: MuScriptor-medium 0.3.0**
  - 307M 파라미터. 코드는 MIT, 가중치는 CC BY-NC 4.0이고 HF 게이트가 있다.
  - 공개 체크포인트 OnP F1: GOAT 0.710, EGDB 0.789, GuitarSet 0.808.
  - Python API로 쓰고, 워커가 가중치를 한 번 로드해 그 패스의 모든 뷰를 처리한다. prelude forcing, batch 1.
  - **dtype은 업스트림 기본값을 따른다:** fp32 가중치 + fp16 autocast, 조건화기는 fp32로 유지 [리뷰]. 다른 dtype은 E24를 통과한 경우에만 쓴다.
  - **오디오는 `(tensor, sr)`로 넘긴다.** 파일 로더가 `.wav`를 표준 `wave` 모듈로 읽는데, `wave`는 float32 WAV를 못 읽는다(`unknown format: 3`, 이 PC에서 확인 [재확인 2026-09-25]).
  - **`instruments`:** 조건화와 동시에 **나머지 악기를 하드 마스크**한다(E3).
    - 기타 뷰: 기타 3클래스 + **S3.5가 존재한다고 판정한** 건반·신스 클래스. 블리드가 기타로 강제되지 않게 하기 위해서다.
    - 전체 믹스와 nonvox: 전체 편성.
  - **타이밍:**
    - 모델 편향으로 최대 약 25 ms의 일정한 지연이 붙는다. M2에서 스펙트럴 플럭스 onset과 비교해 직접 보정한다.
    - 내장 `transcribe_and_postprocess`는 **상수 템포 격자**로 지연을 추정하므로 교차 검증에만 쓴다 [재확인 2026-09-25, muscriptor beats.py].
- **보조:**
  - **Basic Pitch 0.4.0**(bp310, ONNX). Python `note_events`를 읽는다. MIDI 내보내기는 벤딩을 ±2반음에서 자른다.
    - **기본 설정을 그대로 쓰지 않는다.** `DEFAULT_MINIMUM_NOTE_LENGTH_MS = 127.7`이고, 이 값은 86 fps에서 11프레임으로 바뀐다(`min_note_len = round(ms/1000 × sr/hop)`) [재확인 2026-09-25, basic_pitch/inference.py]. 그러면 약 117 BPM보다 빠른 곡의 16분음표, 빠른 리드 런, 고스트 노트, 짧은 뮤트 음이 사라진다. 리드 판별과 벤딩 측정에 쓸 보조 투표자가 리드 음을 체계적으로 잃는다.
    - `minimum_note_length`는 약 30–58 ms(3–5프레임)에서 시작한다(잠정). `onset_threshold`(기본 0.5)와 `frame_threshold`(기본 0.3) [재확인 2026-09-25]는 Basic Pitch 학습에 쓰이지 않은 dev 세트에서 튜닝한다(E23). 쓴 파라미터는 manifest에 기록한다.
  - **f0:** torchcrepe 'full'(Viterbi, 20 cents, 10 ms). 단선율 리드 뷰와 보컬 스템에 쓴다. 베이스 f0(5장)도 같은 워커에서 돌린다.
- **대안:**
  - `--dtype float16` → small(103M) → CPU.
  - YourMT3+(noPS, 별도 venv). RWC-C와 RWC-R의 일부 지표에서 MuScriptor보다 낫다(E19).
  - MuScriptor-large: 기본 로더가 fp32 모델과 state_dict를 모두 GPU에 올려 피크가 약 11 GB다. CPU에서 로드 → fp16 캐스팅 → CUDA 이동으로 패치한 뒤에만 쓴다(E4).
- **실행:** medium 피크 추정 2–3 GB. RTX 4090에서 17배 실시간이고, 2060에서는 **미검증**이다(M2에서 잰다). bf16은 금지한다.
- **위험:**
  - **같은 클래스 기타는 항상 한 트랙으로 합쳐진다.**
  - 같은 음높이·같은 클래스의 동시 음은 표현하지 못한다. 이런 음을 테스트에 남기면 onset F1이 60.4 → 51.8로 떨어진다. 유니즌 판정(R3)에 직접 영향을 준다.
  - 클래스 정확도는 공개되지 않았다. 헤드라인 수치는 in-distribution이다.
  - README는 루바토 녹음이 "상당히" 나쁘다고 적었다.
  - 게이트 문구가 **입력 음악의 권리 보증과 면책**을 요구한다 [재확인 2026-09-25]. 사용자 본인이 판단할 사항이다.
- **근거:** [gap:multi-guitar-muscriptor] 검증, [wf1:transcription-coupling].

### S7 음표 융합·블리드 감점·반복 합의 (M6–M8)

- **출력:** `observations.parquet`. 중복을 제거한 기타 후보 음표로, P(real), 기여한 소스, 증거 벡터, 감점 플래그를 담는다.
- **ROVER식 클러스터:** 같은 음높이(옥타브 검사 후), onset ±50 ms로 묶는다.
- **음표별 증거:**
  - 배음 빗에서 잰 ILD, coherence, centre/S 비. **가설이며 E22에서 검증한다.** 해상도 한계 때문에 다음 규칙을 둔다.
    - n_fft 4096의 bin 간격은 10.8 Hz다. E2(82 Hz)에서 ±30 cents는 약 ±1.4 Hz이고, 인접 반음은 4.9 Hz 떨어져 있다. 그래서 저음의 낮은 배음은 분해되지 않고 코드·베이스 블리드와 겹친다.
    - 저음(대략 E2–A2)은 **3배음 이상만** 쓴다. CQT나 8192 FFT를 쓰고, bin마다 그 음이 차지하는 지배도(다른 후보 음 대비 예상 에너지 비)로 가중한다.
    - coherence는 약 150 ms 평균이 필요하다. **150 ms 미만 음은** 음표별 값 대신 창 단위 팬을 쓴다.
  - 검출된 뷰, 클래스, 동시 음 수, 상대 음역, 길이
  - 벤딩·비브라토, 반복 멤버십, 솔로 게이트, 클라우드 스템
- **감점 (삭제하지 않음):**
  - 보컬 f0를 따라가는 음. 기타가 보컬을 더블링하는 경우가 있으므로 약하게만 감점한다.
  - piano/other가 같은 시간·음높이에서 더 강한 음. piano/other 음은 **S3.5 원시 전사**에서 온다.
  - E2 미만이면서 같은 pitch class의 베이스 음과 겹치는 음. 베이스 음은 **S3.5 원시 베이스 전사**에서 온다(S11 결과를 쓰지 않으므로 순환이 없다).
  - 고립된 옥타브 유령 음.
- **P(real):** v1은 손으로 정한 가중치다. M10에 로지스틱 모델로 바꾸고 곡 단위로 교차검증한다.
- **반복 합의:** 정렬된 반복 마디들이 투표한다. 변주는 감점만 한다.
- **안전망:** nonvox를 전체 편성으로 전사한 결과에서만 나온 기타 음을 저신뢰로 추가한다.
- **위험:** 뷰들이 같은 스템에서 나와 독립이 아니므로 가중치는 학습해야 한다. 과적합.
- **근거:** [wf2:CRITIC] Layer 4, [wf1:transcription-coupling].

### S8 파트 다이어라이저 (M7a–M7b, 핵심) — 4장

- **순서:** 층 → 트랙렛 → 재식별(K 선택) → 구간 단위 더블 병합 → 트윈 검출 → 유니즌 판정 → 음표 소프트 할당 → HMM 평활·반복 구간 헝가리안.
- **만드는 순서:** M7a는 라우터 K + 기호 분할 + Unassigned만으로 Part 뷰 v0를 낸다. 트랙렛·HMM·재식별·반복 헝가리안은 M7b에서 더한다.
- **대안:** 기호 규칙만으로 분할(TabForge `split_lead_rhythm` + Régnier 마디 특징), 또는 단일 'All guitars' 트랙.
- **실행:** CPU. K를 바꾸면 S8–S9만 다시 돈다(목표 2 s 미만).
- **위험:** 발표된 방법이 없어 새 코드이고, 임계값은 미검증이다.

### S9 트랙 배치 (Part 뷰 M7a, Role/Player 뷰 M7c) — 4.9절. CPU, 밀리초.

### S10 점수 기반 재분리·재전사 (선택, max, E18, M10)

- **방법:**
  1. Line 음표로 마스크를 만든다. 배음 빗, 또는 score-informed NMF(Ewert & Müller, libfmp).
  2. Line별 공간 공분산으로 다채널 Wiener 필터를 적용한다(norbert식).
  3. 재전사한다.
  4. S7–S8을 다시 돈다.
  - **독립된 뷰나 백엔드가 동의할 때만** 변경을 채택한다. 최대 2회.
- **대안:** GuideSep(ISMIR 2025, MIT, 16 kHz). 임시 리드를 FluidSynth로 렌더해 mimicry 입력으로 준다. 6 GB 적합성은 미검증이다.
- **위험:**
  - 확증 편향.
  - GuitarDuets에서 추정 음표로 조건화해도 실녹음 두 번째 기타는 1.01 → 1.04 dB로만 올랐다.
  - 실행 시간 +50–100 %.
- **근거:** [wf2:guided-informed].

## 4. 기타 여러 대 분리 전략

### 4.1 용어 (출력 계약의 기초)

| 용어 | 뜻 | 사용자에게 |
|---|---|---|
| Take | 녹음된 연주 1회. 더블 리듬은 테이크가 2–4개 | 안 보임 |
| View | 일부 테이크를 강조한 오디오(centre, S, L, R, 마스크, 반복 잔차, 클라우드). **증거일 뿐** | 청취용 |
| **Line = 기타 파트** | 기타리스트 한 명이 매 순간 쳐야 하는 한 줄기. 곡 전체에서 정체성이 유지되고 쉬어도 된다. 물리적 연주자도, 역할도, 스테레오 위치도 아니다 | **기본 출력 단위** |
| Track | 내보낸 탭 트랙. Part 뷰에서는 Line 1개, Player 뷰에서는 밴드 연주자 1명 | 보임 |

역할(Rhythm, Riff, Lead, Fill, Arpeggio, Tacet)은 **Line의 구간별 라벨**이다. 역할이 바뀌어도 Line을 쪼개지 않는다.

### 4.2 출력 계약 R1–R9

정답 세트도 같은 규칙으로 만든다.

- **R1: 더블·쿼드 테이크는 Line 하나다.**
  - **1차 증거는 라우터 R2 서명이다:** 낮은 coherence, 낮은 hard 비율, 낮은 지연 상관.
  - **음표 일치는 거부권으로만 쓴다.** 구간의 L/R chroma-onset F1이 거부 문턱 미만이면 더블이 아니다. 거부 문턱의 시작값은 0.4다(잠정).
  - **판정 단위는 곡 전체가 아니라 구간이다.** 구간마다 병합한 뒤, 곡 전체 정체성은 재식별(4.6)이 잇는다.
  - **문턱은 측정한 자기 일치도에서 정한다(E6/E22).** 합성 더블(같은 파트 두 테이크)을 SW + MuScriptor에 통과시켜 L/R 전사 F1 분포를 재고, 그 하위 5 백분위수를 거부 문턱으로 쓴다(잠정).
    - v1.1의 "창의 90 % 이상에서 음표 F1 ≥ 0.8"을 버린 이유: 단독 디스토션 기타에서도 전사 F1이 0.71이다(GOAT). 분리 스템의 L/R 채널 뷰는 더 거칠고, 실제 두 테이크는 고스트 노트와 스트럼 세부도 다르다. 그래서 같은 파트여도 0.8을 넘기 어렵고, 가장 흔한 시나리오 A에서 리듬 더블이 Line 2개로 쪼개져 K가 과대 추정된다.
  - 두 테이크는 같은 음의 두 관측이 되어 신뢰도를 올린다.
  - 이름에 "(L/R 더블)"을 붙인다.
- **R2: ADT도 Line 하나다.** 지연 복사본으로, 5–40 ms 상호상관이 0.5를 넘는다. 한 채널로 축약한다.
- **R3: 유니즌.**
  - 다른 곳에서 갈라지는 두 Line은 그대로 유지한다. 유니즌 음은 **두 Line 모두에** 쓰고 `shared`로 표시한다.
  - **판정 (경로 A):** S(리듬)에도 있는 음은 기본적으로 리듬 Line 소유다. 따라서 "centre 음 중 S에 없는 것"이라는 리드 규칙만으로는 유니즌 음이 리드에서 지워지고 쉼표가 생긴다. 이를 막기 위해 S에도 있는 음의 centre/S salience를 본다. 기준은 **그 곡의 리듬만 있는 구간에서 잰 분포**(단일 테이크 모델)다. 이 분포의 상위 95 백분위수를 넘으면 리드도 같은 음을 친 것으로 보고 `shared`로 둔다(문턱 잠정, E22).
  - **판정 (경로 P):** L·R 각각의 전사에 같은 음이 있으면 두 Line 모두에 쓴다.
  - **B/F:** 'Gtr 2가 쉼'과 'Gtr 2가 유니즌'을 가를 증거가 없다. MuScriptor도 같은 음높이·같은 클래스의 동시 음을 하나로 합친다. 그래서 **"유니즌 또는 쉼, 판정 불가"**를 저신뢰로 표시하고 UI 토글을 준다.
  - 기본은 `unison_policy=duplicate`다. `primary_only`는 한쪽에만 쓰고 다른 쪽에는 "Gtr 1과 유니즌" 텍스트를 단다 [안2].
    - 사전 조사의 CRITIC은 양쪽 기타의 유니즌 리프를 "나누지 말고 리듬 탭 하나로" 적고, 연주자별 탭이 필요하면 복제하라고 권했다 [재확인 2026-09-25, wf2_summary.txt]. 이 설계는 Part 뷰가 파트마다 완결된 악보를 줘야 하므로 복제를 기본으로 둔다. 곡 전체가 유니즌이면 아래 규칙대로 CRITIC과 같은 결과가 된다.
  - 정체성은 이웃 창의 팬·음색 연속성으로 판정한다.
  - 곡 전체에서 한 번도 안 갈라지면 R1에 따라 Line 하나로 두고, "Gtr 2로 복제" 버튼을 준다.
- **R4: 옥타브 더블.**
  - 위치나 클래스가 다른 두 층이면 Line 2개로 두고 `octave-unison`을 표시한다.
  - 한 층 안의 옥타브 이음은 한 Line의 셰이프다.
  - 전사기의 옥타브 오류와 구별하기 위해 독립 증거를 요구한다.
- **R5: 하모니 트윈 리드는 Line 2개다.**
  - 조건: 동시에 울리는 단선율 상성부 2개가 2마디 이상 평행 3·4·5·6도로 움직이고, 공통 onset이 60 % 이상.
  - Lead 1은 윗성부(또는 안정된 팬 위치)다. 둘 다 센터면 성부 진행 Viterbi로 가른다.
  - **L·R 모두 단선율 상성부인 창에서는 "S = 리듬" 규칙을 끈다** [wf2:CRITIC 트윈 함정].
- **R6: 일부 구간에만 있는 층** (솔로 오버더브, 브리지 아르페지오, 인트로 어쿠스틱).
  - 다른 층과 **한 번이라도 겹치면** 독립 Line으로 두고, 나머지 구간은 쉼표로 채운다.
  - 안 겹치고 서명이 맞으면 기존 Line에 연결한다.
  - 둘 다 아니면 새 Line을 만들고 "파트 2와 4는 겹친 적이 없습니다. 합칠까요?"라고 묻는다.
- **R7: 역할 변화는 Line을 쪼개지 않는다.** 리듬 연주자의 필, 기타 1대 밴드의 솔로가 해당한다.
- **R8: 비기타는 절대 Line이 아니다.** 건반, 신스, 보컬 블리드는 S7에서 감점하고, 남은 것은 Unassigned로 보낸다.
- **R9: 연주 가능성 상한 [안2].**
  - 한 Line은 한 순간에 코드 셰이프 하나(줄당 1음, 6음 이하, 스팬 ≤5프렛) 또는 단선율 + 더블스톱만 가진다.
  - 넘는 음은 다른 Line이나 Unassigned로 보낸다.
  - 클래스가 다른 동시 층은 절대 합치지 않는다.
- **변주 규칙:**
  - 마디 음표 일치도를 R1과 같은 **자기 일치 분포**에 비춰 판정한다. 전사 잡음만으로 대부분의 마디가 'variant'가 되지 않게 하기 위해서다.
  - 분포의 하위 5 % 미만: 별도 Line 후보.
  - 하위 5–25 %: 'variant'. 기본은 병합하고, 변주 음은 alt 레이어에 두며, 사용자가 결정한다.
  - 그 위: 같은 음(차이는 전사 잡음).
  - 경계값은 E6/E22 보정 뒤 확정한다(잠정).
- **보조 트랙:**
  - `All guitars (reference)`: 채택된 모든 기타 음의 합집합. 항상 내보내고 음소거 상태다. 분할 실패의 안전망이다.
    - **운지하지 않는다.** 기타 2–3 파트의 합집합은 한 사람이 칠 수 없다(동시 6음 초과, 같은 줄 충돌, 서로 다른 튜닝·카포).
    - MIDI와 **음높이로 적는 오선보 전용 트랙**(alphaTex·.gp)으로만 내보내고, 연주 가능성 불변식에서 뺀다.
    - GP5는 음을 줄·프렛으로만 저장하므로 GP5에는 넣지 않는다.
  - `Unassigned (review)`: 최고 사후확률이 τ 미만인 음. τ는 0.4에서 시작해 수정 로그로 보정한다. 0.4–0.6은 호박색으로 표시한다. 같은 이유로 오선보 전용이다.

### 4.3 증거

창은 Beat This! 격자 위 4마디다. 빠른 구간은 2마디이고 구간 경계에 맞춘다. 2마디 vs 4마디는 E9에서 정한다.

- **(a) 라우터 특징.**
- **(b) 경로별 스트림:**
  - A: centre−S / S / L∩R
  - P: L·R 클러스터
  - C·D: 클래스별
  - N: 반복 잔차 / 나머지
  - 항상: 기호 top line / 코드
- **(c) 스트림별 MuScriptor 음표와 클래스.**
- **(d) 음표별 스테레오 특징 (가설, E22):** 배음 빗 기준 ILD, coherence, centre/S 비. 저음은 3배음 이상만, 150 ms 미만 음은 창 단위 팬으로 대신한다(S7). 스트림 사이에 누설이 있어도 음표 하나하나의 위치를 정할 수 있으리라는 기대이고, 검증 전이다.
- **(e) 스트림 서술자:**
  - 팬 중심과 폭, coherence, 클래스 분포
  - 중앙 음역, 2음·3음 이상 비율
  - onset 밀도, 반복 점수, 벤딩·비브라토 비율
  - MFCC 평균·표준편차
  - (선택, E9) **Microsoft CLAP(msclap)** Huang style 임베딩. Tian 등(ISMIR 2025)에서 음색 유사도 1위였지만 4.39 s 이하의 **단독 음**에서만 검증됐다. LAION-CLAP이 아니고, 저장소는 2026-09-15에 보관 처리됐다. 사용자의 톤을 실제로 가를 때만 쓴다.
  - Banquet/PaSST 임베딩은 쓰지 않는다.

### 4.4 파트 개수 추정

두 숫자를 추정한다. **L**은 서로 다른 Line의 수, **C**는 동시에 울리는 Line의 최대 수다(C ≤ L).

1. **더블부터 병합한다(R1/R2).**
2. **하한을 정한다(강건).**
   - 창마다, 음이 8개 이상이면서 서로 일치하지 않는 동시 스트림 수를 센다.
   - "일치하지 않음"은 전사기의 자기 불일치 기준선(R1 보정과 같은 합성 더블 데이터)보다 클 때만 인정한다. 같은 스템에서 나온 뷰들은 기타가 1대여도 분리 인공음 때문에 서로 어긋나기 때문이다.
   - 그 수가 **3개 이상의 창과 2개 이상의 구간**에서 유지될 때만 하한으로 인정한다(잠정). 전곡 최댓값을 쓰면 나쁜 창 하나가 곡 전체 K를 올린다.
3. **하한부터 4까지 각 K로 제약 군집한다(4.6).** 선택 기준:
   - silhouette 또는 eigengap
   - 복잡도 벌점
   - 사전분포 P(K) = {1: .25, 2: .50, 3: .20, 4: .05}. DadaGP 26,181곡 대부분이 기타 2대라는 점에 근거한 가정이다. 록/메탈에 치우쳐 있고 "3 디스토션 + 2 클린"은 포맷 상한일 뿐이므로, 수정 로그로 다시 맞춘다.
   - 사용자가 입력한 파트 수(약한 사전 정보)
   - K=4는 강한 공간 증거가 있을 때만 제안한다. 사람도 동시 음원을 약 3개까지만 안정적으로 센다.
4. **작은 Line은 해체한다.** 2마디 미만이거나 음이 16개 미만이면 가장 가까운 Line이나 Unassigned로 보낸다.
5. **상위 2개 가설을 확률과 함께 보여 준다.** 예: "2파트 0.62 / 3파트 0.27". 가설을 바꾸면 S8–S9만 다시 돈다.
6. **모든 창에서 증거가 약하면** 사전분포 아래 최선의 기호 분할을 만든다. 약하다는 것은 전부 R0이고, 클래스 대비도, 반복 잔차도 없는 경우다. **"자동 분할, 낮은 신뢰도"** 딱지를 붙이고 한 번 클릭으로 합칠 수 있게 한다.

발표된 방법(Tanaka 2020, Li & Zhu 2026, Duan-Han-Pardo)은 모두 K를 입력으로 받는다. 기타 파트 수를 세는 방법은 없으므로 자체 구현이다 [gap:multi-guitar-muscriptor].

### 4.5 라우팅: 시나리오별 분리

| 경로 | 판정 | 파트 가르는 법 | 기대 | 깨지는 경우 |
|---|---|---|---|---|
| **A** | R2 | 리듬 = S 전사(얇거나 콤 필터처럼 들리면 L∩R과 합집합, E8). 리드 = centre 음 중 S에 없는 것(±1반음, ±50 ms) + S에도 있지만 유니즌 판정(R3)을 통과한 음(`shared`) + 높은 centre/S salience + 단선율·음역·벤딩 사전. (선택) MVSEP 101 교차 투표 | 쓸 만함 | 리드 −6 dB 이하, 넓은 딜레이·핑퐁, 쿼드, 너무 타이트한 더블, 센터 보컬 블리드 |
| **P** | R3 | L·R(또는 방위각 클러스터)을 따로 전사. 클러스터×창마다 기호 특징으로 역할을 정함 | 좋음 | 역할 교대, 강한 스테레오 리버브 |

| **ADT** | R1 | 한 채널로 합친 뒤 N 경로 | 검출은 믿을 만함 | 분리 품질은 B 수준 |
| **D** | 클래스 | acoustic/electric 토큰(+선택 Mega-53 단일 스템, MVSEP 66/81) + 기호 확인 | 보통–좋음(증명 안 됨) | 어쿠스틱 필, 일렉 리듬 |

| **E** | 솔로 게이트(규칙판; MERT는 E9) | 게이트 밖은 기존 리듬 Line이 기본. 게이트 안에서만 경로별로 분할(솔로 밑 리듬은 계속되기 때문) | 솔로는 좋음 | 보컬 사이 필, 1마디 필 |

- **MVSEP 101 모노 진단:** 곡당 한 번, 모노 다운믹스도 보낸다. 모노에서 분할이 무너지면 그 모델은 패닝에 의존한다는 뜻이므로 B/F 창에서 가중을 낮춘다.
- **L/R 음표 집합 연산 (E22) [안1]:** R2·R3 창에서 L과 R을 따로 전사해 음표 집합끼리 비교한다.
  - L∩R(양쪽에 같은 음, 낮은 coherence) = 더블된 한 파트
  - L에만, R에만 있는 음 = 한 테이크짜리 파트
  - centre에 있고 S에 없는 음 = 센터 파트. S에도 있는 음은 R3 유니즌 판정을 거친다.
  - 더블 위 트윈 리드도 일부 풀린다. L∩R은 리듬이고, L에만·R에만 있는 평행 상성부는 Lead 1/2다.
  - E22에서 centre−S 방식과 비교해 기본값을 정한다.
- **공통:** RESID(nonvox)도 한 번 전사한다. 한 스트럼 연구에서 잔차가 htdemucs 기타 스템보다 나았다. SW 기준으로는 E2에서 다시 시험한다 [wf1:transcription-coupling].

### 4.6 정체성 추적 (다중 객체 추적 관점, M7b)

1. **층:** 창마다 앞뒤 2마디 맥락을 두고 응집 군집한다.
   - must-link: 한 스트럼 안의 음(onset 약 30 ms 이내), 한 레가토 선율.
   - cannot-link: 공간 서명이 맞지 않는 음.
   - 결과는 창당 1–4층이다. 각 층은 서명(팬, 폭, coherence, 클래스, 음역, 질감, 반복)을 갖는다.
2. **트랙렛:** 인접 창의 층을 서명 거리로 헝가리안 정합한다(생성·소멸 비용 포함). Viterbi 전환 벌점으로 라벨이 1마디마다 뒤집히지 않게 한다. 1마디 뒤집힘은 Régnier 모델의 주 실패였다.
3. **재식별:** 트랙렛을 제약 응집 또는 스펙트럴 군집으로 Line에 묶는다.
   - cannot-link: 시간이 겹치는 트랙렛. R1 병합은 이 단계 전에 끝난다.
   - must-link: 반복 지도가 짝지은 구간에서 음이 일치하는 트랙렛, 서술자가 연속인 인접 창의 같은 경로 스트림.
   - 거리 = 팬(A/P/트윈 경로에서만 높은 가중) + 클래스 + 음역·역할(+CLAP).
4. **HMM/Viterbi 평활:** 역할 교대는 강한 증거가 없는 한 구간 경계에서만 허용한다.
5. **반복 구간 헝가리안:** 1절과 2절을 맞춘다. 맞지 않는 곳은 검토 큐로 보낸다.

이 방법은 Duan-Han-Pardo의 제약 군집을 음높이 수준에서 마디 스트림 수준으로 올리고, 스트림 안에 코드를 허용한 것이다. 공간 화자 분리(Interspeech 2025)의 TDOA는 스튜디오의 진폭 패닝에 맞지 않으므로 ILD와 팬 히스토그램으로 대신한다. **근거:** [gap:multi-guitar-muscriptor] 검증.

### 4.7 음표 단위 판정

음표 하나가 각 Line에 속할 사후확률은 softmax(Σ w·증거)다. 증거 항목:
- 소스 스트림의 Line
- 음표의 팬·coherence를 각 Line의 팬 모델에 비춘 적합도(150 ms 미만 음은 창 단위 팬)
- 클래스
- **기호 역할 사전:**
  - 3음 이상 코드 → 리듬
  - 상음역 단선율, 벤딩, 비브라토 → 리드
  - 코드보다 10반음 이상 높은 윗음은 떼어 낸다
  - Régnier 마디 특징
- 솔로 게이트, 반복 모델 적합도, 연속성
- (선택) 클라우드·커뮤니티 투표

처리 규칙:
- 두 Line의 스트림에 모두 맞는 음은 `shared`, τ 미만인 음은 Unassigned로 간다.
- 가중치는 v1에서 손으로 정한다. M10부터 수정 로그로 로지스틱 회귀를 학습하고 곡 단위 leave-one-out으로 평가한다.
- 사용자가 리드 음 3–5개를 태그하면 힌트로 쓴다. Arranger에서 피치 힌트가 교체 가능한 파트의 정확도를 50.22 → 67.45로 올렸다.

### 4.8 역할 라벨

Line마다 구간별로 {Rhythm, Riff, Lead, Fill, Arpeggio, Tacet} 중 하나를 붙인다. 코드 비율, 음역, 밀도, 벤딩, 반복, 솔로 게이트로 정하고, 탭에는 구간 텍스트로 적는다.

### 4.9 출력 트랙 규칙

**Part 뷰 (기본, M7a)**
- Line 1개가 트랙 1개다.
- **순서와 이름은 결정적으로 정한다.**
  - Gtr 1은 활성 마디가 가장 많은 Line이다. 보통 리듬이다.
  - 나머지는 첫 등장 순서로 번호를 매긴다. 동률이면 팬 위치 왼쪽 → 오른쪽.
  - 이름은 "번호 – 다수 역할 (클래스, 위치)" 형식이다. 예: `Gtr 1 – Rhythm (dist., L/R 더블)`, `Gtr 2 – Lead (dist., centre)`, `Gtr 3 – Clean arp (bridge only)`, `Lead 1 / Lead 2 (harmony)`.
  - 사용자가 파트 이름을 입력했으면 역할·음역·튜닝으로 헝가리안 매칭해 이름을 붙인다.
- 여기에 `All guitars (reference, 음소거, 오선보 전용)`, `Unassigned (음소거, 선택, 오선보 전용)`, `Bass`를 더한다.

**Role 뷰 (M7c)**
- Rhythm / Lead / Lead 2로 다시 묶는다. 연습용이다.

**Player 뷰 (M7c)**
- 기타리스트 수 N은 기본 2다. auto면 C(최대 4)를 쓴다.
- 구간별로 최소 비용 할당을 푼다.
  - 동시에 울리는 Line은 같은 트랙에 넣을 수 없다.
  - 다른 트랙으로 옮기는 것은 구간 경계에서만 허용하고 벌점을 준다.
  - 비용: 역할 전환, 음역 점프, 팬 점프.
  - 우선순위: 리드·고유 라인 > 다른 파트가 덮지 않는 리듬 > 더블·shared.
- shared는 그 음을 치는 모든 연주자에게 복사한다.
- `idle_policy`:
  - `rest` (기본): 원곡에 충실하게 쉰다.
  - `double`: 쉬는 연주자가 더블 리듬을 복제한다. 오버더브가 많은 곡을 기타 2대 밴드가 커버할 때 흔한 방식이다.
- 동시 Line이 N보다 많으면 가장 덜 활성인 Line을 `Gtr extra (overdub)`로 표시해 내보낸다.
- 트랙에 텍스트 마커를 단다. 예: "여기서 Gtr 3 솔로; Gtr 1 리듬 생략".

모든 탭 트랙은 각자의 튜닝, 카포, A4 오프셋을 가진다.

### 4.10 사용자 수정 포인트

- K 설정, Line 병합·분할.
- 음표, 선택 영역, 마디 범위, "여기부터 구간 끝까지"를 재배정한다. 숫자키 1–4, 0은 Unassigned.
- 솔로 구간 표시, shared 토글, B/F의 "유니즌 또는 쉼" 토글, Unassigned 수락·거부.
- 구간별 경로 강제.
- 편성(S3.5) 수정.
- N·idle_policy 변경.
- 리드 음 힌트 태그.

모든 수정은 `edits.jsonl`에 기록되고, 재실행 후 다시 적용되며, S8에 must/cannot-link 제약으로 들어간다. 그래서 1절의 수정이 반복 must-link를 타고 2절에도 퍼진다.

### 4.11 이 단계의 평가

아래 지표를 **모두 시나리오별로** 낸다. 판정은 창 단위의 합성·Tier B 세트에서 하고, Tier A 값은 서술로 보고한다(8.1).
- 파트 수 정확도(정확히 맞은 L의 비율)와 MAE.
- **주 지표: Line별 tick F1과 macro(균형) 할당 정확도.**
  - 헝가리안 매칭 뒤 Line마다 정확도를 내고 평균한다. 음표 가중 정확도는 음이 많은 리듬 Line에 지배되어, 모든 음을 리듬에 넣기만 해도 높게 나올 수 있다. 그래서 참고로만 낸다.
  - 유니즌 음은 그 음을 가진 어느 참조 트랙에 있어도 정답이다.
- **Unassigned는 주 지표에서 오류로 센다.** 어려운 음을 Unassigned로 버려 정확도를 올리는 조작을 막기 위해서다. 따로 **coverage–accuracy 곡선**(τ를 바꿔 가며 할당 비율 대 정확도)을 낸다.
- **모든 문턱은 두 기준선과의 차이로 정의한다.** 다수 클래스 기준선(모든 음을 가장 큰 Line에)과 기호 분할 기준선(8.5).
- Line별 tick F1은 곡 단위 매칭과 구간 오라클 매칭을 함께 내서 내용 오류와 정체성 오류를 가른다.
- role leakage(양방향).
- **유니즌 구간의 shared 정밀도·재현율**(따로).
- 마디 단위 다이어라이제이션 오류: 누락, 오경보, 혼동.
- 정체성 전환 횟수, Unassigned 비율, Player 뷰 연주 불가 위반 수.

**가드:** 분할하면서 음표를 잃으면 안 된다. 합친 기타 tick F1이 분할 전보다 1점 넘게 떨어지면 불합격이다.

## 5. 베이스

**왜 가장 쉬운가:** 베이스 스템은 14.62 dB로 기타(약 9 dB)보다 훨씬 높고, 베이스 라인은 대부분 단선율이다. 주 실패는 **옥타브 오류**다. 근거는 다음과 같다.
- YourMT3+의 RWC-Pop에서 chroma F1과 pitch F1의 격차
- MT3가 베이스를 한 옥타브 높게 전사함
- Slakh 베이스 라벨의 옥타브 오류
- Abeßer: 피치 정확도 0.701 vs chroma 0.82

분리된 팝 스템에서 일렉 베이스를 탭으로 만드는 공개 벤치마크는 없다. **근거:** [gap:bass] 검증.

1. **입력**
   - SW 베이스 스템을 모노로 합친다(44.1 kHz). SCNet 앙상블은 E13에서 정한다.
   - 킥 거부용으로 드럼 스템을 둔다.
   - 블리드를 서로 빼기 위해 **S7의 기타 음표**를 함께 받는다. S7은 S11 결과가 아니라 S3.5 원시 베이스 음을 쓰므로 순환이 없다.
2. **음표 엔진**
   - **(a) MuScriptor-medium, `instruments=acoustic_bass,electric_bass`.**
     - 프렛리스(35)는 acoustic 그룹, 신스 베이스(38/39)는 electric 그룹이다.
     - 실데이터 학습 트랙의 42.8 %가 일렉 베이스다. 베이스 F1은 공개되지 않았으므로 M5에서 검증한다.
     - S3.5 원시 베이스 전사와 입력이 같으므로 캐시를 공유한다.
   - **(b) F0 HMM 분할기 (직접 구현).** CREPE Notes 방식(피치 기울기 + 신뢰도 역수, 반복 음은 onset으로 분할)을 따른다. crepe-notes 패키지는 쓰지 않는다. torchcrepe 백엔드가 fmin 50으로 고정돼 있고, 기본 백엔드는 TF가 필요하며, madmom은 git 설치가 필요하다.
   - **(c) (선택) YourMT3+.**
   - **채택 정책 (E13에서 비교):**
     - **투표자 3개**(YourMT3+ 있음, quality 프로필): **3개 중 2개가 일치**할 때 채택한다(±50 ms, 옥타브 교정 후 같은 음높이). 한 소스에서만 나온 음은 회색 저신뢰로 남긴다.
     - **투표자 2개**(YourMT3+ 없음, 기본 설치): 2-of-3이 두 소스의 AND가 되어 재현율이 떨어지므로 쓰지 않는다. **MuScriptor를 주 소스로 두고**, F0 HMM 경로는 ① 옥타브·피치 교정 ② MuScriptor가 비운 구간에서 안정된 F0 음을 회색 저신뢰로 채우는 데만 쓴다.
3. **옥타브·피치 앵커 (필수, 3-트래커 투표 [안2])**
   - **torchcrepe 'full':** Viterbi, **fmin = 32 Hz**, fmax ≈ 400.
     - **fmin=30은 금지한다.** 최저 bin이 31.70 Hz라 인덱스가 음수가 되고, 유효 bin이 0개가 되어 쓰레기 값이 나온다(검증에서 재현).
     - 기본값 50은 E1–G1을 버린다.
   - **librosa.pyin:** fmin 약 28–30 Hz, 긴 프레임. 학습이 필요 없다.
   - **PESTO 2.0.1:** VQT 27.5 Hz부터, 파라미터 약 130k, LGPLv3. 공개 체크포인트가 **노래(MIR-1K)로 학습**됐고 30–100 Hz 정확도는 측정된 적이 없다. 그래서 한 표만 준다.
   - **판정:** 음표마다 onset 뒤 30–120 ms의 F0 중앙값을 본다.
     - ±12반음 틀리고 트래커 2개 이상이 높은 신뢰도로 동의하면 그 옥타브로 옮긴다.
     - ±1반음 차이면 F0를 믿는다.
   - 저음 B(30.87 Hz)는 PESTO, pyin, Basic Pitch(27.5 Hz부터)에 맡긴다.
   - **쓰지 말 것:** SwiftF0(46.875 Hz부터), FCPE·RMVPE(보컬로 학습, 저음 B를 놓침).
4. **정리**
   - 킥 타격과 겹치면서 안정된 F0가 없는 onset을 버린다. 검증되지 않은 휴리스틱이므로 절제 시험을 거친다.
   - 1 tick보다 짧은 조각은 F0가 이어지면 앞 음에 합친다.
5. **주법 (v1)**
   - 강한 onset인데 F0가 무성: 데드/고스트 'x'. 정답 음을 줘도 22.2 %만 맞았으므로 **제안**으로만 표시한다.
   - F0 글라이드: 슬라이드 또는 HO/PO (제안).
   - 음 안의 피치 변조: 비브라토.
   - **슬랩**은 구간 단위로만 표시한다. 슬랩과 비슬랩은 헷갈리지 않았지만, thumb와 pop은 깨끗한 DI에서도 18–39 % 오분류됐다.
6. **튜닝 후보:** 신뢰할 만한 음의 5–10 백분위수로 본다. **최종 선택은 S13에서 기타 Line과 함께 한다.**
   - 모든 음이 MIDI 28(E1) 이상 → 4현 스탠다드.
   - MIDI 26이 있고 23–25가 없음 → 드롭 D.
   - MIDI 23–25가 있음 → 5현.
   - 곡 전체 다운튠은 기타와 함께 추정한다. 밴드는 대개 같이 튜닝하고, DadaGP도 다운튠이 다른 곡을 거부한다.
   - 사용자가 현 수·튜닝을 덮어쓰면 운지만 다시 계산한다.
7. **줄/프렛 (S13):** (줄, 프렛) 위의 Viterbi.
   - 비용: 4프렛을 넘는 이동, 줄 건너뛰기, 12프렛 초과, 문맥에 따른 개방현, 같은 리프는 같은 운지.
   - 오디오의 줄 음색 단서는 쓰지 않는다. 깨끗한 DI에서도 75.2 %였다.
8. **교차 확인 (S14):** 박마다 베이스 근음과 리듬 Line의 코드를 비교한다. 리듬 Line 코드(S8 이후)가 필요하므로 S14에서 한다. 옥타브나 5도 불일치는 검토 큐로 보낸다.
9. **출력:** 현 수·튜닝이 맞는 GP 베이스 트랙, alphaTex, MIDI, 신뢰도 색. 신스 베이스는 "연주 불가일 수 있음"으로 표시한다.
10. **평가 (M5)**
    - tick F1(정답 격자 기준, 8.4).
    - 옥타브 오류율 = chroma F1 − pitch F1.
    - 줄/프렛 일치.
    - IDMT-SMT-Bass-Single-Track: 17개 라인, 줄/프렛 정답 있음, CC BY-NC-ND, 약 20 MB.
    - FiloBass onset+pitch F1. 기준선은 CREPE Notes 72.89, Basic Pitch 62.73(정밀도 51.4), Melodyne 78.95. Melodyne 값은 정답이 Melodyne 출력에서 출발했으므로 부풀려져 있다. 데이터는 재즈 업라이트다.
    - Tier B 베이스: 참 베이스 트랙을 같은 전사기로 돌린 결과를 참조로 해서 분리가 입힌 손해를 따로 본다.
    - 외부 기준선: Songsterr AI 베이스, Klangio.
    - 유료 수동 대안: Melodyne Assistant 이상. Essential은 MIDI를 내보내지 못하고, 30일 체험이 있다.
11. **기대치:**
    - 스튜디오 록/팝에서 가벼운 수정으로 쓸 만하다고 본다. FiloBass 수준인 70점대 후반–80점대는 짐작일 뿐 **미검증**이다.
    - 빠른 핑거스타일, 슬랩, 신스/디스토션 베이스, 뭉개진 저역에서 나빠진다.
    - 운지는 연주 가능하지만 원곡 베이시스트의 포지션과 같다는 보장은 없다.

## 6. 탭 생성

### 6.1 튜닝·카포 (Line별로 다를 수 있음)

- **T1 미세 오프셋:** S0에서 처리한다(`estimate_tuning` → varispeed). [−0.5, 0.5) 반음만 알 수 있으므로, E 스탠다드와 Eb 스탠다드는 여기서 가를 수 없다. Essentia는 Windows 휠이 없다.
- **T2 기호 가설 탐색 (전사 후):**
  - **기타 가설:**
    - 음정 프로필 {6현 std, 6현 drop, 7현 std, 7현 drop} × 다운튠 {0…−5} × 카포 {0…7}. 카포는 주로 다운튠 0일 때만 고려한다.
    - **오픈 튜닝군** {Open G, Open D, DADGAD} × 카포 {0…7}, 다운튠 0. 이런 곡을 std나 drop으로 강제하면 프렛이 틀린다.
  - **베이스 가설:** {4현 std, 4현 drop, 5현 std} × 다운튠. S11이 낸 후보를 쓴다.
  - **점수 항목:**
    - (a) 가장 낮은 개방현보다 낮은 신뢰 음의 비율(저백분위수 기준)
    - (b) 운지 DP 비용
    - (c) 개방현·0프렛 리프 사용. 드롭 리프는 0-0-0 파워코드에 몰린다.
    - (d) 사전 순위: E std > Eb std > Drop D > D std > Drop C#/C > C std > 오픈 튜닝. 7현은 D2 아래 음이 있을 때만.
    - (e) 다른 Line, 베이스와의 다운튠 일치
    - (f) 사용자가 입력한 튜닝
  - **튜닝 불명:** 최선 가설의 운지 DP 비용이 높으면(문턱 잠정) "튜닝 불명"으로 표시하고 사용자에게 묻는다.
  - **M3 한정:** 아직 Line 분할이 없으므로 합친 기타 음에 튜닝 하나를 가정한다. Line별 탐색은 M7a부터다.
- **가짜 저음 방어 (최저음 통계 전에):**
  - E2 미만 기타 음 중 같은 pitch class의 베이스 음과 겹치는 것(블리드)을 뺀다.
  - 고립된 옥타브 아래 짝(옥타브 오류)을 뺀다.
  - 빼지 않으면 E 스탠다드 곡이 드롭이나 7현으로 잘못 읽힌다.
- **카포 vs 튜닝 올림:** 음높이만으로는 구별할 수 없다. 개방 코드 셰이프 증거로 가르고, 증거가 없으면 사용자에게 묻고 "제안"으로 표시한다.
- **UI:** 상위 2개 가설을 여유와 함께 보여 준다. 덮어쓰면 즉시 운지를 다시 짠다.
- **음정 프로필 등가성:** 다운튠만큼 음을 올려 기본 튜닝에서 운지하고, 라벨만 실제 튜닝으로 바꾼다. 프렛 번호는 같다. 이렇게 하면 운지기 하나로 Drop C와 C std까지 처리된다. 오픈 튜닝은 음정이 달라 별도 프로필이다. 카포 아래 프렛은 금지한다.
- **오디오 튜닝 분류기는 만들지 않는다.** Hulme 5클래스 73.9 %, Rochester 7클래스 71.7–74.2 %로 약하고, D 계열 튜닝을 혼동한다.
- **근거:** [gap:tuning-fret-technique] 검증.

### 6.2 박자·양자화

- **격자:** **비트** 하나당 **48 tick**. 비트 단위는 `grid.json`에 적힌 값(4분 / 점4분 / 8분)이다.
  - 4분음표 비트: 한 박 안에서 16분 셋잇단(8), 32분 셋잇단(4), 32분음표(6), 64분음표(3)를 모두 표현할 수 있다. Klangio의 박당 12 sub-beat 설계를 확장한 것이다. 12로는 정박 32분음표를 표현할 수 없다.
  - 점4분음표 비트(6/8·12/8): 8분음표 = 16 tick, 16분음표 = 8 tick.
  - **GP 변환은 비트 단위 기준으로 한다.** GP는 4분음표당 960 tick이므로, 4분 비트면 1 tick = 20 GP tick, 점4분 비트면 1 tick = 30 GP tick이다.
- **방법:**
  - 박마다 Viterbi로 2분할(16/32분)과 3분할(셋잇단) 중 하나를 고른다. onset 잔차와 전환 벌점을 최소화한다.
  - 음 길이는 다음 onset 또는 offset까지로 하고, 최소 1/32로 둔다.
  - 박이나 마디를 넘으면 붙임줄로 잇는다.
- **셋잇단 느낌:** 구간 안에서 8분 뒷박 onset이 박의 약 2/3 지점에 몰리면 셋잇단 느낌을 켜고 정박 8분으로 적는다. alphaTex는 `\tf triplet8th`(`\tripletFeel`이 아님), GP5는 `MeasureHeader.tripletFeel`이다. swingogram을 단순화한 방식이다. 12/8 가설과 겹치면 S2의 복합 박자 판정을 따르고 UI 토글을 준다.
- **두 시간축:**
  - 악보에는 읽기 쉽게 반올림한 템포를 쓰고, 구간 단위로 지속될 때만 바꾼다.
  - 실제 시각은 마디별 `\sync` 포인트로 남겨 커서와 백킹이 원곡을 따라가게 한다.
  - 못갖춘마디는 `\ac`, 구간은 `\section`으로 적는다.
  - 양자화 전 연주 MIDI도 항상 함께 내보낸다.
- **조성과 철자:** music21 9.9의 조성 추정기(Krumhansl-Schmuckler, Temperley-Kostka-Payne 등).
- **공개 양자화기를 쓰지 않는 이유:**
  - MIDI2ScoreTransformer: 피아노 전용, Python 3.11 필요, 라이선스 없음.
  - PM2S: 피아노로 학습.
  - Klangio: 코드와 가중치가 없음.
  - MuseScore 4: 3의 양자화 패널을 없앴고, MIDI 가져오기의 MUSTER가 47.90이다.
- **평가:** MUSTER식 onset 오류. 사용자 곡 목표는 25 이하(잠정). 격자 품질은 음표 지표와 따로 낸다(8.4).
- **근거:** [gap:notation-output] 검증.

### 6.3 줄/프렛 배정

- **1단계 (M3): 자체 Viterbi**
  - **상태:** 단음의 (줄, 프렛), 또는 코드 운지(줄당 1음, 스팬 4–5프렛, 바레 허용, DFS로 열거).
  - **비용:**
    - 손 위치 이동, 줄 건너뛰기, 고프렛 벌점
    - 문맥에 따른 개방현 보너스
    - 레가토 후보는 같은 줄 유지
    - 리듬 Line은 코드 셰이프 템플릿(파워코드, 개방코드, E형·A형 바레, 트라이어드, sus/add9)을 저비용 상태로 둔다
    - 반복 구간은 같은 운지
  - **프렛 신뢰도:** 1위 경로와 2위 경로의 비용 차이. UI에서 대안을 순환해 볼 수 있다.
  - **적용 대상:** 탭 트랙(Line, 베이스)만. `All guitars`와 Unassigned는 운지하지 않는다(4.2).
- **기준선:** tuttut(MIT). PyPI 0.0.6은 numpy==1.23.2 등을 고정하므로 git HEAD에서 설치하거나 코드를 가져와 쓴다.
- **목표:** 음높이가 맞은 음에서 줄/프렛 일치 ≥75 %. 참고로 DadaGP에서 Guitar Pro 76.58, A* 78.92, Fretting-Transformer 81.58이다.
  - **평가 방법:** Line 분할 전(M3)에는 ① **오라클 Line 분할**(예측 음을 가장 가까운 참조 트랙에 배정한 뒤 트랙별로 운지·튜닝을 평가) ② 기타 1대 곡과 Tier C 줄 정답(GuitarSet 등) 중 하나로 잰다. 합친 음 전체의 운지는 평가하지 않는다.
- **2단계 (M12, 선택): 학습된 T5 운지기**
  - Fretting-Transformer 구조(d_model 128, 3+3층)와 튜닝·카포 토큰, 음높이 유효성 제약 디코딩을 쓴다. Hsu 등은 77.10(재구현 기준선 71.78)으로 원 논문보다 낮았다.
  - 공식 가중치가 없으므로 직접 학습한다.
  - 데이터: SynthTab JAMS(CC BY-NC), DadaGP(요청), HF `vldsavelyev/guitar_tab`(라이선스 표기 없음).
  - DadaGP는 카포를 프렛 번호에 녹여 저장하고 곡당 다운튠이 하나다. 그래서 카포와 Line별 튜닝은 합성 증강으로 만든다.
  - 입력을 열화시킨다: 음 20–30 % 삭제, 옥타브 오류, 타이밍 흔들림.
  - DP보다 3점 이상 나을 때만 교체한다. 7현과 베이스는 DP를 유지한다.
- **오디오 기반 줄 분류는 쓰지 않는다.** 공개 수치(.78–.93)는 단독 DI 음에서 나왔고, 교차 악기면 약 .78이다.

### 6.4 주법

- **1층 (M9): f0 규칙**
  - torchcrepe Viterbi F0를 쓴다. Line 오디오가 있으면 그것을, 없으면 centre나 반복 잔차 같은 리드 성향의 뷰를 쓴다.
  - **확정 표기:**
    - 벤딩: onset 뒤 새 onset 없이 약 80 cents 이상 상승. ½, 온음, 1½로 양자화한다.
    - 릴리스, 프리벤딩
    - 비브라토: 4–8 Hz, 깊이 약 20 cents 이상
  - **제안만:**
    - 슬라이드, HO/PO. 후보 선택만으로는 깨끗한 솔로에서도 정밀도가 15–30 %였다(Chen/Su/Yang Table 1a [재확인 2026-09-25]). 그래서 약한 onset 검사와 운지기의 같은 줄 제약을 추가로 통과해야 한다.
    - 데드 노트 'x'
    - 팜뮤트 후보: 리듬 Line에서 짧은 감쇠 + 낮은 스펙트럼 중심
    - 하모닉스: 문맥상 불가능하게 높은 음
    - 렛 링
  - **표시 규칙:** 측정 정밀도 ≥0.7인 클래스만 기본으로 보인다. 실제 믹스에서 규칙만으로 버틴 것은 벤딩뿐이었다(F 67.3). 깨끗한 데이터로 학습한 SVM은 오히려 나빠졌다. 임계값은 E15에서 보정한다.
  - Basic Pitch 벤딩(1/3반음, 86 fps)은 2차 의견이다. Gaussian(std 5 bin) 때문에 넓은 벤딩에 불리하다. 최소 음 길이를 낮춘 설정(S6)이어야 짧은 벤딩 음이 남는다.
- **2층 (M12, 선택): 온셋별 소형 CNN**
  - 팜뮤트, 자연·피치 하모닉스, 데드 노트를 맡는다.
  - 학습 데이터: EG-IPT(CC BY 4.0, DI 포함), Guitar-TECHS(CC BY 4.0), GOAT(요청).
  - **우리 분리기의 인공음으로 증강**한다.
  - TART의 95.9 %는 단독 데이터에서 잰 값이고 코드도 없으므로 기대하지 않는다.

### 6.5 코드 차트와 가독성

- **코드 인식:** 리듬 Line의 박 또는 반 마디 단위로 길이 가중 pitch class 히스토그램을 템플릿(maj, min, 5, 7, maj7, m7, sus2, sus4, dim, add9)에 맞춘다. 동률이면 베이스 근음으로 가르고, HMM으로 코드 변화에 벌점을 준다.
- **베이스 교차 확인:** 같은 단계에서 5장 8번을 수행한다.
- **출력:** GP 코드 다이어그램, alphaTex 코드, 텍스트 차트.
- **반복 기호:** 반복 구간은 반복 기호로 쓰고 반복 합의 음을 넣는다.
- **대안 보기 (선택):** 저신뢰 리듬 구간은 코드 + 스트럼 격자로 볼 수 있다. Lukoianov & Klapuri 스트럼 모델은 비공개라 자체 onset으로 근사하고, 다운/업 추정은 저신뢰로 표시한다.
- **저신뢰 표시:** GP5는 음표별 신뢰도를 담지 못하므로 마디에 '?' 텍스트를 넣을 수 있다(선택).

- 구간 반복, 50–100 % 감속(피치 보존), 카운트인.
- sync가 틀리면 alphaTab Media Sync Editor로 고친다.

**신뢰도**
- 피치·파트·프렛 신뢰도 중 하나를 골라 색으로 칠한다.
- 임계값 슬라이더.

**편집 (키 2타 이내, M4a)**

## 8. 평가 체계

### 8.1 원칙과 결정 규칙

- 모든 선택지는 `docs/decisions.md`의 실험 E#로 관리한다.
- **사전 등록:** E#마다 실험 전에 주 지표, **최소 검출 효과(MDE)**, 데이터, 분석 방법을 적는다. 결과를 보고 지표를 바꾸지 않는다.
- **판정 수준을 둘로 나눈다.**
  - **컴포넌트 게이트 (기본값 채택):** 합성 리믹스, Tier B 리믹스, KV·DI 리믹스(Tier B')를 합친 **창 단위 세트(수백 창)**에서 판정한다. 마디 단위로 추정하고, **곡 블록 부트스트랩**(곡을 단위로 재표집, 10k)으로 95 % CI를 낸다. 채택 조건은 둘 다다.
    1. CI가 0을 제외하고, 점추정이 MDE 이상이다.
    2. 어떤 시나리오 하위 세트도 CI 상한이 −2점 아래로 내려가지 않는다(명백한 퇴행 없음).
  - **Tier A (end-to-end 점검과 편집 시간):** 시나리오당 1–3곡이라 판정에 쓰지 않는다. 시나리오별 수치는 **서술 통계**로만 보고하고, 명백한 퇴행(여러 곡에서 같은 방향으로 크게 나빠짐)이 보이면 조사한다.
- **비용이 큰 요소**(실행 1.5배 이상, 클라우드 비용, venv 추가)는 +1.5 note/tick F1 또는 +3 macro 할당 정확도 이상을 추가로 요구한다.
- **통계력 한계:** Tier A 곡 10–15개로는 약 3점 미만 차이를 가리지 못한다. 컴포넌트 세트에서도 CI가 0을 포함하면 "판단 보류"로 기록하고 기본값을 유지한다.
- Tier A의 약 1/3은 test로 떼어 두고 마일스톤 게이트에서만 연다.
- SDR과 청취 평가는 진단 열로만 쓴다.
- **학습 데이터 오염:** 세트마다 각 전사기·분리기의 학습에 들어갔는지 `eval/contamination.md` 표로 관리한다. 확인하지 못한 칸은 '불명'으로 두고, 불명인 세트로는 그 모델의 절대 성능을 주장하지 않는다.

**Tier A 구축 규칙 (정답 비용 때문에):**
- 곡 전체가 아니라 **구간 2–3개**(예: 벌스+코러스+솔로, 약 32마디)만 정답으로 만든다.
- **GP 파일이 이미 있는 곡을 우선한다**(공식 GP, 사용자가 이미 가진 검증된 GP). Songsterr Plus에서 파일을 받을 수 있는지와 그것이 약관 범위 안인지는 **미검증**이다. 확인 전에는 쓰지 않는다.
- PDF만 있으면 TuxGuitar로 다시 입력해야 한다. 기타 2대와 베이스면 음이 수백–수천 개라 **곡당 3–8시간**이 든다(리뷰 추정, 미검증). 예산에 이 비용을 적고, 가능하면 피한다.
- CD·구입 음원을 우선한다.
- 늘리는 순서는 M1b를 따른다: M2 전 2–3곡(GP 있는 곡) → M6 전 5곡(A·P·B/F 각 1곡 이상) → M8 전 8–12곡.
- 최종 목표 구성: A 3+, P 2+, B/C 2+, D 1, F 1, 트윈/유니즌 1, 비표준 튜닝 2.
- 시스템 출력을 고친 탭은 dev에만 쓴다.

**GuitarSet를 전사 판정에 쓰지 않는 이유:** Basic Pitch의 GuitarSet 분할은 `random.shuffle`에 선택적 seed를 넘겨 만든다 [재확인 2026-09-25, basic_pitch/data/datasets/guitarset.py]. 논문의 테스트 트랙 ID가 공개되지 않았다면 [리뷰] "테스트 분할만" 고를 수 없고, 어느 트랙이든 학습 데이터였을 수 있다. 컴포넌트 판정은 전사기마다 **학습에 쓰이지 않았다고 확인된 세트**로 한다. 리뷰는 EGDB, IDMT-SMT-Guitar, GOAT(요청)를 제안했다. 이 제안은 **미검증**이다. MuScriptor는 GOAT·EGDB·GuitarSet 헤드라인 수치가 in-distribution이라 이 세트들의 학습 분할을 봤을 가능성이 크다. 그래서 MuScriptor에는 공식 test 분할만 쓰고, 학습 목록은 M1a에서 모델 카드와 논문으로 확인한다.

### 8.3 정답 준비 (GP가 있으면 곡당 1–2시간 목표, 추정)

1. GP3–5는 PyGuitarPro로, `.gp`/`.gpx`/MusicXML은 alphaTab(Node)으로 가져와 반복과 다른 엔딩을 펼친다. D.S.와 코다는 `gt.yaml`의 마디 지도로 처리한다.
2. `gt.yaml`에 다음을 적는다.
   - **정답 구간 목록**(마디 범위). 평가는 이 구간 안에서만 한다.
   - 구간별 시나리오 태그
   - 튜닝과 카포
   - **Line 지도:** 참조 트랙 중 어느 것이 더블, 유니즌, 트윈, 오버더브인지. 4.2와 같은 규칙을 쓴다.
   - 연주자 매핑
   - 구간별 역할 {lead, rhythm, both, silent}
   - 버전 플래그
3. **정렬 (Beat This!와 독립):** 정답의 마디 시각을 평가 대상인 Beat This!로 만들면 M3의 비트 지표가 자기 자신과 비교되어 부풀려진다. 그래서 다음 절차를 쓴다.
   1. 참조 GP를 오디오로 렌더한다(alphaTab Audio Export, 없으면 FluidSynth).
   2. 믹스와 렌더를 onset 강화 chroma DTW로 맞춘다. synctoolbox 1.4.2를 쓴다(MIT 분류자, Python ≥3.10 <3.15 [재확인 2026-09-25, PyPI]).
   3. 사람이 다운비트를 탭해 보정한다. M4a 전에는 외부 라벨 도구(예: Audacity 라벨 트랙)로 찍은 텍스트를 가져온다.
   4. 결과는 **정답 템포맵**(마디·박 시각)이다. 박 사이는 선형 보간한다.
   5. (선택) ±70 ms 안의 스템 onset에 스냅한다.
4. `align_check.wav`(믹스 + 참조 onset 클릭)를 사람이 듣고 승인한다.
5. 곡당 실제 소요 시간을 기록해 8.2의 예산을 고친다.

### 8.4 지표 (mir_eval 0.8.x + 자체 구현)

1. **tick F1 (M3 이후 주 지표, 정답 격자 기준):** 예측 onset(초)을 **정답 템포맵**으로 옮겨 정답 좌표(마디, tick @48)로 바꾼다. 같은 음높이이고 ±50 ms에 해당하는 tick 범위 안이면 일치로 본다. 시스템 자신의 격자 오류(반 박 위상, 다운비트 이동)가 음표 점수에 섞이지 않는다.
   - v1.1의 "(마디, tick ±1 @48)"은 시스템과 정답이 각자의 격자에서 비교됐다. 그래서 반 박 위상 오류 하나로 구간 전체가 0점이 됐고, ±1 tick은 120 BPM에서 약 10 ms라 사실상 양자화 결과가 같아야 했다.
2. **기보 일치 (격자·양자화 품질):** 마디 번호를 맞춘 구간에서, 시스템이 양자화한 (마디, tick)이 정답과 정확히 같은 음의 비율. 11번 리듬 지표와 함께 **따로** 보고한다.
3. **시간 note F1:** onset+pitch 50 ms/50 cents, 100 ms, offset 포함판.
4. chroma F1과 옥타브 오류율(chroma − pitch).
5. Line별 지표(곡 헝가리안 + 구간 오라클).
6. 파트 수 정확도와 MAE.
7. **macro(균형) 할당 정확도**(Unassigned = 오류)와 coverage–accuracy 곡선. 음표 가중 정확도는 참고.
8. role leakage(양방향).
9. 마디 다이어라이제이션 오류.
10. Unassigned 비율.
11. 유니즌 구간의 shared 정밀도·재현율.
12. 음높이가 맞은 음의 줄/프렛 일치(탭 트랙만, M3는 오라클 Line 분할), 튜닝·카포 정확도, 연주 가능성 100 % 불변식(탭 트랙만), (정답이 있으면) 탭 F1/TDR.
13. **리듬:** 정답 템포맵 대비 beat·downbeat F1(70 ms), 마디 수, 박자표·비트 단위·못갖춘마디, MUSTER식 onset 오류.
14. 주법 클래스별 정밀도·재현율(벤딩 우선), 코드 라벨 정확도.
15. **베이스:** tick F1, 옥타브 오류율, 줄/프렛, 데드 노트 재현율.
16. **사람 지표 (가장 중요):**
    - 파트별로 "칠 수 있음"까지 걸린 편집 시간(분).
    - **헤드라인 기준선은 세 조건이다:** ① 도구 없이 처음부터 채보 ② 외부 AI 초안(Songsterr AI·Klangio)에서 수정 ③ gtab 초안에서 수정. 도구 버전끼리의 비교는 그 다음이다. 같은 구간을 여러 조건으로 치면 학습 효과가 생기므로, 곡을 구간으로 나눠 조건마다 다른 구간을 맡기고 순서를 돌린다.
    - 마디당 편집 수와 **편집 종류 분포**. 종류마다 원인 단계를 귀속해 다음 개선 대상을 정한다.
      - 파트 재배정 → S8
      - 옥타브 수정 → S6/S7/베이스 앵커
      - 줄 변경 → S13
      - tick·다운비트 이동 → S2/S12
      - 삭제 → S7 오탐
      - 추가 → S6 누락
      - 편성 수정 → S3.5
    - 1–5점 쓸모 평가
17. **자원:** 단계별 피크 VRAM(reserved·NVML), Shared Usage 증가 여부, 시간, 캐시 적중, 클라우드 비용.
18. **보정:** 파트·피치 신뢰도의 ECE, 검토 큐 상위 20 %가 담은 실제 오류 비율.

### 8.5 기준선 (모든 리포트에 포함)

- **B0:** 전체 믹스에 MuScriptor를 돌려 기타를 한 트랙으로 합친 것. 바닥선이다. S3.5의 믹스 전사를 그대로 쓴다.

- **다수 클래스 할당:** 모든 기타 음을 가장 큰 Line에 넣은 것. macro 할당 정확도의 바닥선이다.
- **기호 분할만:** TabForge `split_lead_rhythm` 방식.
- **외부 (사용자가 직접 돌릴 때만):**

- **사람:** 처음부터 채보한 시간(8.4 16번).

**결정성:**
- **GPU 산출물이 캐시된 상태에서 CPU 단계는 byte 단위로 같은 결과를 내야 한다.**
- GPU 단계는 비트 단위로 결정적이지 않다. fp16 autocast, cuBLAS, 자기회귀 디코딩 때문이고, 그리디 디코딩에서 토큰 하나가 뒤집히면 음표가 바뀐다. 그래서 GPU 단계는 결정성 플래그(`CUBLAS_WORKSPACE_CONFIG`, `torch.use_deterministic_algorithms`)를 시도하되, 캐시를 지운 재실행은 **반올림한 음표 목록을 허용 오차로** 비교한다(예: onset 10 ms, 음표 수 차이 0.5 % 이내, 잠정).

- **단계 키** = sha256(단계 이름 + 코드 버전 + 해석된 파라미터 + 입력 해시 + 모델 SHA256).
- 임시 폴더에 쓴 뒤 원자적으로 rename한다. 완료된 manifest가 있으면 건너뛴다.
- 파라미터 변형은 `stages/<name>/<key12>/`에 나란히 남는다. A/B 비교가 쉽다.
- S3.5와 S6, S3.5와 S11처럼 입력이 같은 전사는 캐시를 공유한다.
- 클라우드 결과는 (백엔드, 입력 해시, 옵션)으로 캐시하므로 업로드는 곡당 1회다.
- 배치 모드: 여러 곡에 한 단계씩 돌려 모델 로드를 한 번으로 줄인다.
- `gtab gc`로 정리하고, `gtab clean --archive`로 float 스템을 24-bit FLAC으로 바꾸고 게인을 저장한다. 작업 하나가 float 상태에서 1–1.5 GB, 보관 후 약 0.3 GB다. 보관 후 복원 오차는 M2에서 검증한다.

### 9.5 GPU 메모리 (엄격한 순차 실행)

- core 오케스트레이터는 torch를 불러오지 않는다.
- GPU 단계는 모두 자식 프로세스로 돈다: `<gpu venv>\Scripts\python.exe -m gtab.workers.<name> request.json`.
- **venv의 python.exe는 런처다.** 이 PC의 CPython 3.10 venv에서 `Scripts\python.exe`가 기본 인터프리터 `Python310\python.exe`를 자식 프로세스로 띄우는 것을 확인했다. 그 안의 `sys._base_executable`은 기본 인터프리터 경로를 가리켰다 [재확인 2026-09-25]. 실제로 CUDA를 쓰는 것은 이 자식이다. uv venv도 같은지는 M0 doctor에서 확인한다(미검증).
  - 워커는 Windows **Job Object**(`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`)에 넣어 띄운다. 런처가 띄운 자식도 같은 Job에 속하므로, 취소나 타임아웃 때 함께 끝난다.
  - `data\gpu.lock`(filelock)은 **Job 안의 모든 프로세스가 끝날 때까지** 쥔다. 부모만 죽고 자식이 VRAM을 쥔 채 남으면 '모델 하나' 보장이 깨지고 다음 워커가 Sysmem Fallback에 빠지기 때문이다.
  - NVIDIA 프로그램별 프로필(Sysmem Fallback 정책)은 venv 경로가 아니라 **`sys._base_executable`이 가리키는 기본 인터프리터 경로**에 건다. doctor가 그 경로를 출력한다.
- 락으로 **GPU에 모델 하나**만 올린다. CLI와 UI를 동시에 실행해도 지켜진다.
- **워커 동작:**
  1. 모델 하나를 로드한다.
  2. 그 작업의 입력을 전부 처리한다(예: MuScriptor 패스 2에서 뷰 5–8개).
  3. 결과와 `result.json`을 쓴다. 담는 값: 버전, 시간, `torch.cuda.max_memory_allocated`, **`max_memory_reserved`**, NVML 프로세스별 사용량 피크(자식 PID 기준), 실행 전후 Shared Usage, 경고.
  4. 종료한다. VRAM이 완전히 반환되므로 단편화와 누수가 없다.
- **측정 원칙:**
  - `max_memory_allocated`만으로는 부족하다. 캐싱 할당자의 reserved 여분, WDDM의 CUDA 컨텍스트, cuDNN/cuBLAS 워크스페이스가 빠진다 [리뷰]. 판정은 reserved와 NVML 값으로 한다.
  - Windows 성능 카운터 `GPU Process Memory(pid_*)\Shared Usage`와 `GPU Adapter Memory(*)\Shared Usage`·`Dedicated Usage`를 읽는다(이 PC에서 카운터 이름 확인 [재확인 2026-09-25]). **워커 실행 중 Shared Usage가 늘면 실패로 본다.** Sysmem Fallback으로 시스템 RAM에 넘친 것이기 때문이다.
- **예산:** 전체 VRAM − 다른 프로세스 점유(NVML) − 여유 약 0.7 GB(데스크톱·컨텍스트용, 추정, M2에서 잰다). 다른 앱을 닫은 상태의 목표 피크는 reserved 기준 **4.5 GB 이하**다(잠정).
- **VRAM 경합 [안2]:**
  - 안2 작성 시점 점검에서 LoL·Discord·Slack·Steam·Claude 앱·셸이 6.14 GB 중 3.39 GB를 쓰고 있었다(재측정하지 않음). 이 상태면 위 예산은 약 2 GB다.
  - 워커는 시작할 때 `torch.cuda.mem_get_info()`와 NVML로 여유를 재고, 백엔드별 설정 사다리에서 예산에 들어가는 가장 큰 칸을 고른다. 예: SW 청크 588,800 → 352,256 → 262,144, MuScriptor medium → small.
  - 안 들어가면 설정에 따라 **대기(기본, 백오프)**, 명확한 오류, 작은 모델만 CPU 중 하나를 한다.
  - `gtab queue run --overnight`로 PC를 쓰지 않는 시간에 몰아 돌린다.
  - doctor는 GPU를 쓰는 다른 프로세스와 측정해 둔 단계별 필요량을 보여 준다.
- **max 프로필 순서:** Beat This! → SW → (SCNet XL) → **MuScriptor 패스 1**(S3.5: 믹스 전체 편성, 기타 스템 모노, 베이스, piano+other) → (MERT, E9 통과 시) → CenterWide → (커뮤니티 lead/rhythm) → **MuScriptor 패스 2**(S6: 모든 뷰) → (large, 리드 뷰) → f0 워커(torchcrepe: 보컬·리드 뷰·베이스, PESTO: 베이스; + CPU pyin) → (YourMT3+) → CPU S7 → S11 → S8 이후 → (정제 루프). Basic Pitch(bp310)는 CPU/ONNX라 S5 뒤 아무 때나 돈다.
- **워커 안 규칙:**
  - **dtype은 백엔드별로 업스트림 기본값을 따른다.** SW/MSST는 fp32 가중치 + AMP, MuScriptor는 fp32 가중치 + fp16 autocast(조건화기 fp32) [리뷰].
  - 가중치 fp16 캐스팅은 E24(또는 E4)에서 품질 저하가 없음을 확인한 백엔드에만 쓴다. MuScriptor-large 로더 패치가 그런 경우다. RoFormer를 순수 fp16 가중치로 돌리는 것은 검증되지 않았고, 정규화나 어텐션에서 오버플로가 날 수 있다.
  - 로드는 CPU에서 하고 CUDA로 옮긴다. `torch.inference_mode()`, batch 1. **Turing에서 bf16 금지.**
- **OOM 사다리:** 청크를 절반으로(hop 배수 유지) → CPU(경고) → (설정 시) 클라우드 → 건너뜀. 모두 기록한다. Sysmem Fallback이 켜져 있으면 OOM 예외가 나지 않으므로, **Shared Usage 증가나 처리량 급락**도 사다리를 내려가는 조건으로 둔다.
- **느려짐 감시:** Windows NVIDIA의 **Sysmem Fallback**은 OOM을 조용한 약 10배 감속으로 바꾼다. Shared Usage와 처리량으로 감지해 경고한다. 설정 변경은 사용자 몫이다(12장).
- **시스템 RAM 16 GB:** 게임과 브라우저를 함께 켰을 때 커밋 한도가 바닥난 전례가 있다. 프로세스당 무거운 모델 하나, 블록 단위 WAV 읽기, 스템 사본 금지, STFT는 창 단위로 돌린다.

### 9.6 백엔드 교체

### 9.7 테스트

- 지표 항등식: 항등, 삭제, 옥타브, 라벨 교환.
- **지표 조작 방지:** Unassigned만 늘리면 macro 정확도가 오르지 않는다. 모든 음을 한 Line에 넣으면 다수 클래스 기준선과 같다.
- **정답 격자 변환:** 템포를 흔든 합성 연주에서 시스템 격자 오류가 음표 지표에 새지 않는다.
- DSP 픽스처: router_exp와 repet 이식.
- 디코딩: `codec_exp3.py`의 큰 Opus에서 1.0을 넘는 샘플이 유지되는지.
- 양자화기: 격자를 아는 합성 연주로. 6/8·12/8과 4/4 셔플 픽스처.
- 운지 DP 불변식(탭 트랙만), 튜닝 탐색(오픈 튜닝 포함).
- 왕복: score.json → alphaTex → .gp → alphaTab 재로드, .gp5 → PyGuitarPro.
- 편집 로그 재생 해시.
- **DAG 비순환:** 단계 명세에 순환이 있으면 실행기가 시작 전에 실패한다.
- **워커 정리:** 워커를 강제 종료하면 런처의 자식 인터프리터까지 끝나고, 그 뒤에 락이 풀린다.
- **torchcrepe fmin ≥31.7 고정.**
- **MuScriptor에 float32 경로가 아닌 텐서를 전달하는지.**
- **Basic Pitch `minimum_note_length`가 기본값(127.7 ms)이 아닌지.**
- **베이스 투표자 2개일 때 AND 정책이 쓰이지 않는지.**
- 20초 골든 클립 스모크 테스트.
- 병합 전 `gtab eval run --suite quick`(dev 3곡 또는 합성 세트).

### 9.8 Windows 함정

- **콘솔 cp949:** 모든 워커에 `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`을 준다. stdout 래핑은 한 곳에서만 한다.
- **PowerShell 5.1:** BOM 없는 UTF-8 `.ps1`을 cp949로 읽는다. 스크립트는 ASCII로 쓰고 로직은 `.py`에 둔다. 토큰은 `$env:HF_TOKEN` 문법이다.
- **경로:** ASCII만 쓴다.
- **torchaudio 2.9+:** `load()`가 TorchCodec을 거쳐 shared FFmpeg가 필요하다. ffmpeg로 WAV를 만들고 soundfile로 읽어 **배열/텐서**로 넘긴다.
- **표준 `wave`는 float32 WAV를 못 읽는다**(이 PC에서 확인 [재확인 2026-09-25]). MuScriptor에는 텐서를 넘긴다.
- **venv python.exe는 런처다**(9.5). 프로세스 감시, NVIDIA 프로필, 강제 종료는 자식 인터프리터 기준으로 한다.
- **MuScriptor GPU 설치:** `--torch-backend=cu128`(uvx)를 쓰거나, cu128 torch를 먼저 깐 venv에 pip로 설치한다. 기본 백엔드는 CPU다.
- panns 등의 wget 호출은 실패하므로 파일을 수동으로 받는다.
- **Python 3.10 EOL(2026-10):** gpu venv는 3.12로, yt-dlp는 exe로 분리했다.

## 12. 사용자 결정 필요 사항

### 지금 (M0 전)

1. **설치 승인:**
   - uv, uv가 관리하는 Python 3.12. 전역 3.10은 그대로 두고, 3.10은 2026-10에 EOL이다.
   - torch 2.11.0+cu128(약 2.5–3.5 GB). 문제가 생기면 2.8.0+cu128로 내리는 것에 동의하는지, 또는 처음부터 2.14+cu130을 원하는지.
   - 위치 `D:\gtab`.
2. **YouTube 경로 — 결정됨(2026-09-30 사용자 결정): 기본 켜짐.** 사용자가 아래 고지를 받고 기본 켜기를 요청했다. 당시 질문은 다음과 같았다.
   - 로컬 파일만 쓸지(권장), 아니면 YouTube 경로를 켤지.
   - 켜면: yt-dlp.exe nightly와 Node를 JS 런타임으로 쓴다. 이때 **기본 경로에서도 YouTube의 JS 챌린지를 푼다.** 독일 법원이 이것을 기술적 보호조치 우회로 판단했다는 보도가 있고, 한국법 적용은 미검증이다. 약관 위반 위험과 함께 본인 책임임에 동의하는지.
   - PO 토큰과 쿠키는 그 위의 추가 위험이다. 따로 옵트인하지 않는 한 끈다.
3. **UI 언어:** 한국어, 영어, 둘 다 중 선택.

### M1 전

4. **Tier B 데이터 (본인만 가능):** Cambridge-MT 교육용 약관에 동의하고 록 곡 2곡 이상(각 0.5–2 GB)을 받을지. MedleyDB 접근을 요청할지(Zenodo). 개인 프로젝트가 "연구용" 조건에 맞는지는 본인이 판단한다. M1a와 M2의 결정이 이 데이터에 기댄다.
5. **정답 곡 (Tier A, 점진):**
   - M2 전에는 **GP 파일이 이미 있는 곡** 2–3곡이면 된다. M6 전 5곡(A·P·B/F 각 1곡 이상), M8 전 8–12곡으로 늘린다.
   - 곡마다 오디오(CD나 구입 음원 우선)와 **기계가 읽을 수 있는** 신뢰 탭이 필요하다. 곡 전체가 아니라 **구간 2–3개**(약 32마디)만 정답으로 만든다.
   - 비용: GP가 있으면 곡당 약 1–2시간(정렬·라벨·다운비트 탭, 추정). **PDF만 있으면 TuxGuitar로 다시 입력해야 해서 곡당 3–8시간**(추정)이 든다. 감수할지, GP가 있는 곡만 쓸지.
   - 처음 2곡은 정답 구간의 다운비트를 전부 직접 탭해야 한다(정렬 도구 검증).
   - 편집 시간(분)을 재 줄 수 있는지.
   - 가장 중요한 시나리오를 알려 준다: 메탈 더블, 트윈 리드, 클린/어쿠스틱 레이어, 라이브.
   - (선택) Karaoke-Version Custom Backing Track을 살지($2.99/곡). **원곡 정답이 아니라** 그 스템으로 만든 리믹스용 정답(Tier B')이 된다.
6. **밴드 설정:**
   - 기타리스트 수 N.
   - 쉬는 연주자: rest 또는 double.
   - 유니즌 표기: duplicate 또는 primary_only(사전 조사 CRITIC 방식에 가까움).
   - Unassigned 트랙을 내보낼지.
   - 오버더브 전용 파트: `Gtr extra`로 둘지, 버릴지, 합칠지.
   - 기본 뷰: Part(권장), Role, Player 중 선택.
7. **악기·튜닝·편성 사전 정보:** 6/7현 기타, 4/5현 베이스, 평소 쓰는 튜닝(E std, Eb, Drop D, 오픈 튜닝 등), 자주 채보할 곡에 건반·신스가 있는지.
8. **리듬 파트 표기:** 음표 탭만 쓸지, 코드 차트와 스트럼도 함께 쓸지.

### M2 전

9. **Hugging Face:** 본인 계정으로 MuScriptor 게이트(CC BY-NC 4.0, 입력 음악의 권리 보증·면책)를 직접 수락하고 `hf auth login`을 실행해야 한다. Claude가 대신할 수 없다. 거부하면 Basic Pitch와 YourMT3+로 내려가 품질이 떨어진다.
10. **라이선스 불명 가중치:** SW와 CenterWide를 개인용으로 수락할지. 수락하지 않으면 xlance `gtr_mss`(MIT 태그, SW 파생)와 Bertom 또는 IPD/ILD 센터 분할로 대체한다.
11. **NVIDIA 설정 (본인이 직접):** 'CUDA - Sysmem Fallback Policy'를 'Prefer No Sysmem Fallback'으로 바꿀지. 바꾸면 조용한 감속 대신 명확한 OOM이 난다. 프로그램별로 걸 때는 **venv의 python.exe가 아니라 doctor가 알려 주는 기본 인터프리터 경로**에 걸어야 한다. M2는 켠 상태와 끈 상태를 둘 다 시험하므로, 시험 동안 잠시 바꿔 줄 수 있는지도 알려 준다.
12. **VRAM 부족 정책:** 게임 등으로 VRAM이 모자랄 때 대기(기본), 작고 느린 설정, 작은 모델만 CPU 중 무엇을 쓸지. 밤샘 큐를 쓸지.

### 해당 마일스톤 전

13. **(M3)** Guitar Pro 8이 있는지, 아니면 TuxGuitar와 alphaTab만 쓸지. MuseScore 4를 설치할지.
14. **(M4a) 사람 기준선:** "처음부터 채보" 조건을 직접 해 줄 수 있는지(곡 2개를 구간으로 나눠 진행). "외부 AI 초안" 조건을 위해 Songsterr Plus 1개월(AI 50건)이나 Klangio를 살지. 계정은 본인이 만든다. 사지 않으면 두 조건만 잰다.
15. **(M5–M9) 데이터셋 접근 요청 (본인만 가능):** GOAT, MoisesDB, (M12용) DadaGP.
16. **(M7b) MERT 솔로 분류기:** 라이선스 표기가 없는 체크포인트(약 1.13 GB)와 CC BY-NC 백본을 개인용으로 받아 이식할지. 이식하지 않으면 규칙판 솔로 게이트만 쓴다.
17. **(M8) 클라우드:** MVSEP 토큰(무료, 제3자에게 업로드, MP3 출력)과 Music.AI 키(유료)를 만들지. 작업마다 업로드 동의를 어떻게 받을지.
18. **(M8) 본인 DI 녹음:** 오디오 인터페이스가 있다면, 알려진 파트를 DI로 녹음해 리앰프하고 알려진 패닝으로 섞을지. 가장 좋은 컴포넌트 정답(Tier B')이 된다.
19. **(M10) 실행 시간 예산:** max 프로필에 곡당 60분이 괜찮은지, quality를 기본으로 할지.
20. **(M11) 메타데이터 조회:** ytmusicapi, SponsorBlock 같은 메타데이터 전용 조회(오디오 업로드 없음)를 허용할지(YouTube 경로를 켠 경우), AcoustID 키를 등록할지. Songsterr는 수동 입력만 받는다.
21. **(M12) GPU 임대:** 게이트가 발동할 때만 약 $15–40를 쓸지.
