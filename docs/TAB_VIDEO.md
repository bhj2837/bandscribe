# 탭 영상에서 정답 탭 뽑기 — 설계 (2026-10-25)

목적: 기타 분리와 음 인식을 재려면 J-pop 정답이 필요하다(지금 0곡). 밴드스코어 PDF 는 비싸고 검증이 오래 걸리므로, 유튜브에 커버와 함께
탭을 보여 주는 영상에서 탭을 **음 데이터(마디 · 열 · 줄 · 프렛)** 로 뽑아 `bandscribe eval sheets` 의 실버 정답으로 쓴다.
결과는 지금 악보 JSON(`data/tmp/sheets_*/gtr1.json` 형식)과 같은 꼴로 내서 채점 코드를 그대로 쓴다.

## 0. 원칙

- **정확도를 재지 않은 추출은 정답으로 쓰지 않는다.** 공개 도구들(아래 출처)은 탭 화면을 PDF 그림으로 모으는 데서 멈추거나, 압축 영상의 프렛
  숫자 OCR 오류를 사용자가 찾을 수 없다고 적는다. 그래서 이 설계의 중심은 OCR 보다 **검증 관문**이다.
- 영상 · 프레임 · 뽑은 탭은 모두 `data/` 에만 둔다(커밋 금지). 탭은 영상 제작자의 채보다 — 개인 평가용으로만 쓰고 공유하지 않는다. 유튜브 다운로드의
  약관 위험은 이미 동의 기록(`data/config.toml [consent] youtube`)이 있지만, 영상(화면)까지 받는 것은 새 다운로드라 목록을 사용자가 승인한다.
- 실버 정답이다: 결속밴드 악보와 섞지 않고 따로 표를 만든다(`docs/decisions.md` 실버 규칙).

## 1. 영상의 종류 (처리 순서)

| 종류 | 화면 | 어려운 점 | 우선 |
|---|---|---|---|
| A. Guitar Pro · TuxGuitar · Songsterr 재생 화면 녹화 | 오선 + 탭, 커서가 움직이고 쪽이 넘어가거나 가로로 흐른다. 글꼴이 일정하다 | 쪽 보기에서는 반복이 펼쳐지지 않는다 → 커서 순서로 편다 | 1 |
| B. 직접 만든 탭 띠(영상 아래에 탭이 흐름) | 6줄 위 숫자, 가로 스크롤 | 글꼴 · 색이 제각각, 마디 번호 없음 | 2 |
| C. 손 · 지판 영상만(탭 없음) | — | 손 모양 인식이 필요 | 하지 않음 |

## 2. 처리 단계

1. **수집 목록** `data/eval/tabvid/videos.yaml` (로컬): 곡(작업 키), URL, 파트(gtr1 / gtr2 / bass / all), 튜닝 · 카포(사람이 한 줄 적는다 —
   머리말 OCR 보다 싸고 정확하다), 영상 종류, 메모. 후보는 yt-dlp 검색(`ytsearch`)으로 뽑아 사용자에게 보이고, 사용자가 고른 것만 받는다.
2. **받기:** yt-dlp(이미 있음)로 1080p 영상 + 오디오. 기존 YouTube 대기 간격을 지킨다.
3. **프레임:** ffmpeg 로 초당 2–4장, 앞 프레임과 거의 같은 것은 버린다(탭 영역 차이로).
4. **탭 줄 찾기:** 가로 투영(행별 어두운 화소 합)에서 같은 간격의 평행선 6개(베이스 4–5개)를 찾고 'TAB' 표시로 확인한다. numpy · scipy 만
   쓴다(OpenCV 없음).
5. **마디 · 열:** 세로 마디선으로 마디를 자르고, A 형은 마디 번호(위 왼쪽 숫자)로 마디를 식별한다. 숫자 덩어리의 x 위치로 열(같은 시각)을 묶는다.
   리듬은 1차에서 열 순서와 대략의 위치만 쓴다(지금 채점도 마디 안 음높이 묶음이다).
6. **글리프 읽기:** 줄 위 연결 성분을 0–24, x(뮤트), 그리고 h · p · / · \ · b · ~ · PM 같은 주법 표시로 분류한다. 분류기는 (a) 글꼴 템플릿 맞춤,
   부족하면 (b) GPU 환경 torch 의 작은 CNN. 학습 데이터는 7의 합성 영상에서 정답 라벨째 얻는다(새 다운로드 없음).
7. **같은 마디 여러 번 읽기:** 한 마디가 여러 프레임에 나오면 프레임별 읽기를 투표로 합치고, 갈리는 글리프는 '불확실'로 남긴다.
8. **연주 순서:** A 형은 재생 커서(색 막대 · 강조 상자)가 지나간 마디 순서 = 연주 순서라 반복이 저절로 펼쳐진다. 커서가 없으면 마디 번호 순서 +
   사람이 적은 반복 구조.
9. **출력:** 마디마다 numerator · 열 · (줄, 프렛, dead, tied) — 지금 악보 JSON 과 같은 형식. `data/eval/sheets/songs.yaml` 에 `truth: silver_video`
   로 올린다.

## 3. 검증 관문 (이게 통과해야 정답으로 쓴다)

1. **합성 영상으로 먼저 잰다(다운로드 없음):** 우리 `export/tab/score.gp`(정답을 아는 탭)를 뷰어(alphaTab)로 그려 Edge 헤드리스로 화면을 찍고,
   유튜브 비슷한 H.264 비트레이트로 다시 압축해 영상을 만든다. 거기서 뽑은 탭과 원래 탭을 비교하면 **글리프 정확도 · 마디 정확도**가 정확히 나온다.
2. **진짜 영상에서도 정답으로 잰다:** 결속밴드 6곡은 이미 PDF 악보 정답이 있다. 같은 곡의 탭 영상에서 뽑은 탭을 PDF 정답과 비교하면 실제 영상의
   추출 정확도가 나온다(채보자가 달라 생기는 차이는 마디 F1 로 따로 본다).
3. **영상 자기 소리와 대조:** 뽑은 탭을 소리로 만들어(뷰어의 탭 신스 · alphaTab) 영상 오디오와 마디별 크로마로 맞춘다. A 형 영상은 소리가 탭 재생인
   경우가 많아, 맞게 읽었으면 거의 일치한다. 낮은 마디는 '의심'으로 표시한다.
4. **프레임 투표 일치율, 글리프 신뢰도.**
5. **사람 확인:** 의심 마디만 영상 프레임과 뽑은 탭을 나란히 보여 준다(나중에 뷰어 화면).
- 통과 기준(사전 등록 예정): 합성 영상에서 글리프 정확도 99 % 이상, 마디 정확도 95 % 이상. 진짜 영상은 결속밴드 곡에서 PDF 정답과의 마디 F1 이
  같은 곡의 두 채보 사이 차이 수준. 곡마다 의심 마디 10 % 이하인 탭만 실버 정답으로 쓴다.

## 4. 단계와 비용

| 단계 | 내용 | 다운로드 | 비용 |
|---|---|---|---|
| P1 | 합성 영상 만들기(뷰어 → Edge 스크린샷 → ffmpeg), 줄 · 마디 · 글리프 읽기, 투표, JSON 출력. 합성에서 정확도 측정 | 없음 | CPU, 작업 1–2일 |
| P2 | 사용자가 고른 진짜 영상 3–5개(결속밴드 1–2곡 = 정확도 측정용, 怪獣の花唄 기타, 狭心症 베이스) | 영상 3–5개(승인) | CPU |
| P3 | 오디오 대조 관문, 의심 마디 표시 | 없음 | CPU |
| P4 | 곡 늘리기(사용자 목록), J-pop 실버 표 | 영상(승인) | — |

대안(쓰지 않음): 비전 언어 모델로 프레임을 읽는 방식(공개 도구 하나가 Claude vision API 를 쓴다)은 API 키와 비용이 들고, 로컬 모델은 6 GB VRAM
에 무겁다. 글꼴이 일정한 A 형에서 템플릿 · 작은 CNN 이 모자랄 때만 다시 본다.

## 5. 진행 (2026-10-25, P1 + P2 일부)

코드: `bandscribe/tabvid/`(glyphs · staff · video · sheet · fetch · align)와 `bandscribe tabvid` 명령, 테스트 `tests/test_tabvid.py`(합성 탭
그림 · 합성 화음 소리 22개, `-m smoke`). 영상 · 소리 · 프레임 · 읽은 탭은 `data/eval/tabvid/` 에만 있다.

```
bandscribe tabvid search --job <작업 키> [--part bass]                     # 후보 영상: 원곡과 길이 차이, 다른 판 표기
bandscribe tabvid read <YouTube 주소 | id | 영상 파일 | 프레임 폴더> -n 6 -n 4     # 기타 6줄, 베이스 4줄; 트랙마다 판정
bandscribe tabvid align data/eval/tabvid/read/<id>_n6.json --job <작업 키>   # 같은 판 · 축약판 · 다른 곡
bandscribe tabvid score data/eval/tabvid/read/<id>_n6.json --job <작업 키> [--track 1]   # 우리 결과를 영상 탭으로 채점
bandscribe tabvid review data/eval/tabvid/read/<id>_n6.json [--bars 100-120]   # 의심 마디: 영상 그림 ↔ 읽은 탭 (HTML)
bandscribe tabvid compare data/eval/tabvid/read/<id>_n6_t1.json <악보 JSON> --agree 0.8
```

`read` 는 줄 높이(트랙)마다 `<id>_n<줄>.json`(마디 · 열 · 프레임 일치)과 악보 JSON 형식의 파트 `<id>_n<줄>_t<트랙>.json` 을 낸다. 영상 받기는 YouTube
입력과 같은 규칙(우리 설정만, 쿠키 없음, 5초 간격, `youtube.enabled`)에 영상 형식(1080p 이하, 소리 없음)만 다르다.

**설계에서 바뀐 것:**
- 글리프는 연결 성분이 아니라 **상자 먼저** 읽는다. GP · alphaTab · TuxGuitar · Songsterr 는 프렛 숫자를 줄을 끊는 흰 상자 위에 그린다. 줄의 회색이
  끊긴 곳이 숫자 후보이고, 상자 안 잉크를 빈 열로 잘라 글꼴 템플릿(Windows 글꼴 12종 + Bravura 쉼표)과 정규 상관으로 맞춘다. 압축 영상에서 연결
  성분은 흐린 획 · 기둥 · 붙임줄 호에 깨졌다. CNN 은 쓰지 않았다(아래 수치로 아직 필요 없음).
- 연주 순서는 커서가 아니라 **쪽 + 마디 번호**로 잡는다. 같은 마디선 배치(±3 px)이고 내용이 절반 이상 같은 프레임들이 한 쪽이다. 마디 번호는 쪽
  안에서 투표하고, 쪽의 첫 번호는 앞 쪽 끝 근처에서 읽은 번호와 가장 잘 맞는 값으로 정한다. '24' 는 124 에 반만 맞는다(앞자리가 자주 빠진다). 앞
  쪽에서 크게 건너뛰는 시작은 정확히 읽힌 번호로만 정당화된다.
- **한 화면의 여러 탭 줄:** 마디선이 같은 줄들은 한 시스템의 여러 파트(Rika: 기타1 · 기타2)이고 시스템 위에 한 번 적힌 마디 번호를 나눠 쓴다.
  마디선이 다른 줄은 다음 시스템(악보 쪽 형식: 같은 파트가 이어짐)이다 — 단 마디 번호가 대부분 위 시스템과 겹치면 같은 시간의 다른 파트(Rika 브리지의
  아르페지오 기타)다. 트랙 = 시스템 안의 순서이고 트랙마다 따로 쪽 · 번호 · 투표를 한다. 숫자가 없는 줄(쉬는 파트)도 다른 탭과 마디선이 같으면 탭으로
  둔다(빼면 아래 파트들이 한 칸씩 올라간다).
- 한 화면에서 가장 넓은 줄간격의 0.8배보다 좁은 줄은 오선보로 보고 버린다(본 형식 모두 탭 줄간격이 오선보보다 넓다: JINZO 20 / 13.5 px, Rika 17 /
  약 12, GP 쪽 13.2 / 8.8). 탭 줄이 시작하는 곳의 세로줄은 위 · 아래로 이어져도(시스템을 잇는 선) 첫 마디선으로 본다.
- 마디 번호: 마디선 오른쪽(GP)이든 마디선 위 가운데(Rika)든 읽는다. 탭 첫 줄 바로 위까지 보되 첫 줄보다 완전히 위에 있는 성분만 후보로 하고(1번 줄 프렛
  숫자는 줄 아래로 내려온다), 긴 세로 · 가로선(커서 상자 · 재생 커서 · 오선)은 먼저 지운다. 탭 위 16 줄간격까지 찾되 패널 경계(배경 밝기가 40 넘게 다른 0.5 줄간격 이상의
  띠 — 영상 위의 탭 띠)에서 멈추고, 배경은 탭 줄 자체의 배경으로 잡는다. 숫자 템플릿만 쓴다(Bravura 8분쉼표가 7 과 닮았다). 번호 행은 확실한
  숫자(점수 0.7 이상)로 고르고, 고른 행 안에서는 0.45 까지 받는다 — Ryo Higuchi 의 옅은 세리프 '5' 는 0.55 쯤이다(그 영상 프레임 6장의 번호 22개:
  15–21 → 22 맞음, Rika 베이스 11장 43개: 36 → 42). 세로 닫기와 대비 늘리기도 시험했지만 Rika 베이스 번호를 망쳐 넣지 않았다.
- 탭 줄은 어두운 행 50 % + n줄 등간격으로 찾고, 그게 아무것도 못 찾을 때만 밝은 배경 대비 가는 행 30 % 로 찾는다(둘을 함께 쓰면 JINZO 의 오선보 +
  덧줄 행이 가짜 6줄이 됐다). 두 극성(어두운 테마)을 본다. **줄 수는 정확히 n**: 같은 간격의 줄이 위 · 아래에 더 있으면 그 묶음이 아니다(6줄 기타
  안의 4줄은 베이스가 아니다). 줄 사이 회색이 끊긴 곳이 2개 이상이고 배경이 밝은 줄만 탭으로 본다. 0.8 줄간격보다 가까운 겹세로줄은 한 마디선이다.
- 쪽: 배치가 같으면 내용이 비슷한지(마디마다 (줄, 프렛) 묶음 60 % 이상 겹침)로 같은 쪽을 묶고, 마디 번호가 2개 이상 같은 값만큼 밀렸으면(그대로인 마디
  없이) 새 쪽이다(같은 리프가 다음 쪽에 반복됨). 마디 판독은 프레임들의 음 단위 투표다(가장 흔한 열 수의 판독들에서 과반인 음).
- **리듬 슬래시**(Rika 의 리듬 기타: 코드 모양 한 번 뒤 사선): 탭 안까지 올라온 기둥 + 그 끝에서 오른쪽 위로 오르는 가는 획 + 숫자 없음 → 앞 코드
  모양을 다시 친 열로 넣는다(죽은 줄은 빼고 — 밴드스코어가 반복 스트럼을 그렇게 적는다). `slash` 표시가 남는다.
- 숫자가 아닌 것 걸러 내기: 줄을 덮는 기호(TAB 기호의 'A' — 상자 여백이 없고 좁다), 온 · 2분쉼표(채움 85 % 초과 사각형), 숫자 상자 가장자리에
  닿아 밖으로 이어지는 붙임줄 호(가장자리부터 가는 열을 깎는다), 상자 위 · 아래로 이어지는 기둥, 가장 큰 조각의 0.7배보다 낮은 조각(벤딩 화살표의
  촉), 0.12 줄간격보다 가는 실선.
- 붙은 상자(`13 1313 13`, 16분음표 `12 12 12 12 …` 처럼 가까운 숫자): 틈을 30 줄간격까지 받고, 프렛(0–24)이 아닌 숫자열은 양쪽이 모두 프렛이 되는
  곳에서, 없으면 가장 넓은 간격에서 나눈다.

  마디(60 % · 20 %), 마디 시간 간격이 고른 마디(60 % · 30 %); 마디 8개 미만은 못 씀. 잰 영상: Rika · JINZO 쓸 수 있음, あいろな · tabs & chords 의심,
  베이스코어 狭心症 못 씀.
- **영상 찾기** (`tabvid search --job`): 곡 제목 + TAB + 파트로 검색해 원곡과 길이가 가까운 순으로, 다른 판 표기 · 'TAB' 없음 · 길이 5 % 이상 차이를
  표시한다(받지 않음). 怪獣の花唄 에서 replica 를 표시하고 원곡 길이의 후보 4개(jsVbdzZvLks · jQqoXllvvIg 포함)를 위에 올렸다.

- **주법 표시:** 숫자 오른쪽에서 시작해 탭 위로 1.5 줄간격 넘게 솟는 가는 획 = 벤딩 화살표(1번 줄 위 붙임줄 호는 0.65 쯤만 솟는다), 숫자 바로
  앞 · 뒤(1.2 줄간격)에서 그 줄을 비스듬히 가로지르는 가는 직선 = 슬라이드. 열마다 `bend` · `slide` 로 남고 프레임 투표를 거쳐 악보 JSON 열에 실린다.
  줄을 지울 때 획이 가로지르는 화소는 남긴다(지우면 사선이 두 토막). 같은 채보자 PDF 의 'full' 표시와 마디별로 맞추면 벤딩 99개 중 78개, 오탐 2개
  (정밀도 0.975 · 재현율 0.79); 벤딩이 없는 JINZO · GKA 기타1 에서 오탐 0. 슬라이드는 PDF 가 일부만 'sl.' 글자로 적어(글자 없는 사선은 글자 추출에
  없음) 정답으로 못 쓰고, 표본 마디를 눈으로 보니 모두 진짜 슬라이드였다(`／10`, `(11)＼`, `5／` 등).
- **사람 확인** (`tabvid review`, 관문 3-5): 마디마다 가장 오래 보인 프레임 · 마디 상자 · 탭 줄 위치를 남겨, 의심 마디(또는 범위 · 전부)를 영상에서 잘라낸
  그림과 읽은 탭(글자 탭, b 벤딩 · / 슬라이드)을 나란히 놓은 HTML 을 `data/eval/tabvid/review/` 에 만든다(영상 그림은 로컬에만).

**남은 것:** 해머링 · 풀링(H · P) 표시와 박자표 읽기, 탭 소리로 마디마다 대조(3-3 의 나머지), 베이스코어처럼 번호가 시스템 첫 마디에만 크게 있는 형식,
저해상도(682p) 영상.
