====================================================================================================
AREA: youtube-ingest

[SUMMARY]
State of yt-dlp (2026-09-24). The latest PyPI release is 2026.8.19, which requires Python >=3.10. Its `[default]` extra pins yt-dlp-ejs==0.8.0. Since the 2025-11-12 announcement, full YouTube support needs an external JS runtime to solve YouTube's JavaScript challenges. Deno is recommended and is the only runtime enabled by default (minimum 2.3.0). Node works too (minimum 22.0.0) but must be enabled with `--js-runtimes node`. This machine already has Node v24.10.0, ffmpeg/ffprobe 8.0.1 and winget, but no yt-dlp and no deno.

- **Clients and PO tokens.** The master source's default clients are ('visionos','web'). Without a JS runtime yt-dlp falls back to ('visionos',) and warns that some formats may be missing. PO tokens (GVS) are enforced for web, mweb, web_music and similar clients. The web client gets only SABR formats. Tokens are bound to each video ID. The featured fallback plugin is bgutil-ytdlp-pot-provider (GPL-3.0). Premium subscribers do not need a GVS PO token.
- **Cookies.** The yt-dlp wiki says logging in risks an account ban. Guest sessions are rate-limited at about 300 videos/hour.
- **Python support.** yt-dlp will drop Python 3.10 shortly after its October 2026 end of life. The Windows .exe moves to Python 3.14, which needs Windows 10 or newer. The project venv should therefore use Python 3.11+, or use the standalone yt-dlp.exe, which bundles EJS and self-updates.

Audio formats. Only a community format table and yt-dlp source/issues back these; nothing official.
- Normal YouTube serves Opus 251 (~128 kbps VBR, WebM) and AAC-LC 140 (128 kbps).
- 141 (AAC 256k) and 774 (Opus ~256k) are YouTube Music Premium only and need cookies.
- 'Stable volume' DRC variants exist (format_id suffix -drc). yt-dlp ranks them lower, and the default sort prefers opus over aac, so `-f bestaudio` normally picks non-DRC 251.
- Opus is at most 20 kHz fullband and decodes at 48 kHz. The original sample rate is not preserved, so resample to 44.1 kHz for the SW model, whose config uses 44100.

Codecs vs separation.
- No study measures separation SDR directly on YouTube-rate Opus/AAC input. Indirect evidence: MSRBench found AAC/MP3 at 64/128 kbps barely moved a BSRNN restorer (guitar SI-SNR -19.4 to -19.6 dB).
- My own synthetic test used idealised double-tracked guitar plus centre lead, run locally with ffmpeg. Opus 128/160k, AAC 128k and MP3 128k round trips kept waveform SNR at 22.6–25.2 dB and S=(L-R)/2 SNR at 21.3–23.4 dB. The stereo router features changed by 0.1 dB or less.
- So codec noise sits well below a ~9 dB-SDR guitar separator's error, and does not break stereo routing.
- In libopus CELT, intensity stereo is off above an equivalent rate of 134 kbps. Between 106 and 134 kbps it touches only frequencies of 15.6 kHz and up.
- Averaging aligned Opus and AAC decodes gained a further +2.4 dB SNR in the synthetic test, because the two codecs' errors were uncorrelated (r=0.01). This is a low-priority option.

Loudness matters more than codec.
- Jeon et al. (ISMIR 2022) measured commercial masters at a median of -7.96 LUFS, against -16.02 for musdb-hq. Every separator they tested lost SDR on loud versions of musdb. For example, Demucs v3-B's average dropped from 10.11 to 9.26, and drums from 11.73 to 9.22. Loudness-normalising the input recovered most of the loss (9.94).
- The SW config has inference normalize: false, so the separator receives raw level.
- Clipping. In float builds, libopus applies soft clipping when decoding to int16; ffmpeg's native opus/aac decoders output float. In my synthetic loud master (RMS -8 dBFS), the Opus 128k decode peaked at +1.02 dBFS and AAC 128k at +1.58 dBFS. Always decode to float32 and apply gain in float.

Picking the version.
- YouTube 'Art Tracks' are auto-generated from album releases (sound recording plus album art). yt-dlp spots them by a description ending in 'Auto-generated by YouTube.' and fills track, artists, album and release_year.
- ytmusicapi (MIT) can search with filter='songs' vs 'videos' (videoType OMV). Its get_watch_playlist returns a 'counterpart' (the song/video switcher). The docs example shows the Wonderwall MV at 4:38 against the album song at 4:19.
- Live versions can be flagged with live_status/was_live plus title keywords.

Trimming non-music.
- SponsorBlock has a crowdsourced 'music_offtopic' (Non-Music Section) category. yt-dlp can mark or remove it, and queries it with a 4-character SHA-256 hash prefix. The database is CC BY-NC-SA 4.0.
- inaSpeechSegmenter (MIT, won MIREX 2018 speech detection) labels speech/music/noise. It counts speech over music as speech and singing as music.
- When an album counterpart exists, aligning the MV to it is the most reliable trim.

Metadata and hints.
- yt-dlp exposes title, track, artist(s), album, release_year, duration, chapters, live_status and categories.
- Songsterr's public search endpoint (unofficial; I tested it live today) returns each tab track's part name, for example 'Lead Guitar', 'Rhythm Guitar', 'Rhythm Guitar 2' and 'Bass', with tuning as MIDI note arrays. That gives a prior on tuning and on how many guitar parts to expect.
- AcoustID (free for non-commercial use, needs an app key, at most 3 requests/second) identifies local files.
- Spotify's audio-features and audio-analysis endpoints have been closed to new apps since 2024-11-27.

Legal. YouTube's Korean ToS (effective 2022-01-05) forbid accessing, reproducing or downloading content except as the Service expressly authorises or with prior written permission. They also forbid automated access. So local audio files must be a first-class input, and CD/purchased lossless audio is preferred.

[RECOMMENDATIONS]
 - Ingestion contract: accept either a YouTube URL or a local file. Always emit two things. (1) The untouched original container (e.g. 251.webm), never re-encoded, so avoid `-x --audio-format mp3` and `-t mp3`. (2) `mix_44k_f32.wav`: stereo, float32, 44.1 kHz via soxr, no clipping. Also write `meta.json` with source id, format_id/acodec/abr/asr, title/track/artists/album/release_year/duration/chapters/live_status, measured LUFS and true peak, applied gain, trim offsets and warnings. Cache by video ID or file hash.
 - Installation: keep yt-dlp out of the CUDA-torch environment's lifecycle. Use the standalone yt-dlp.exe (bundles EJS, `yt-dlp -U`), or a Python 3.11+ venv with `pip install -U "yt-dlp[default]"`. Python 3.10 support ends shortly after October 2026. Put `--js-runtimes node` in the yt-dlp config (Node 24 is present). Update yt-dlp automatically before retrying after any extraction error.
 - Failure ladder, with no cookies by default. First, default clients plus the JS runtime. Next, `yt-dlp -U` and retry. Next, the bgutil PO-token provider plugin. Last, cookies from a throwaway or private-window export, only if the user opts in, with the documented ban-risk warning shown. Treat 141/774 (Premium 256k) as out of scope: in the synthetic test codec noise sits far below separator error, and cookies carry account risk.
 - Format selector: `ba[format_id!*=drc][acodec=opus]/ba[format_id!*=drc]/ba`. Log what was chosen. Optional later experiment: also fetch 140 and average the aligned decodes (+2.4 dB codec SNR on synthetic data). Keep this behind a flag and validate with note-F1 before enabling.
 - Version resolution before any separation. If the description does not end in 'Auto-generated by YouTube.', query ytmusicapi get_watch_playlist(videoId)['counterpart'], or search(filter='songs') on the artist and track. Show the MV and album candidates with durations and let the user choose, defaulting to the album Art Track for studio covers. Flag live versions (live_status/was_live, or titles containing live, 라이브, 직캠, concert, session, cover) rather than silently replacing them, since a band may want the live arrangement.
 - Non-music trimming, in priority order. (1) If an album counterpart exists, cross-correlate or chroma-DTW-align the MV to it; this gives exact song boundaries. (2) SponsorBlock music_offtopic segments via `--sponsorblock-mark` (non-destructive), then cut the float WAV. (3) inaSpeechSegmenter or an energy check on the separated drums+bass+guitar stems. Cut only leading and trailing non-music. Mid-song skits get masked, not removed, so tab timestamps still map to the original video.
 - Level handling: decode to float, measure integrated LUFS and true peak (ffmpeg ebur128 or pyloudnorm), and apply a float gain so the peak sits at or below -1 dBFS. A/B test whether normalising to about -14 to -16 LUFS before BS-RoFormer SW improves guitar and bass stems; SW has normalize: false, and Jeon et al. show loud-master losses that normalisation largely recovers. Store the gain so stems can be restored to the original level.
 - Input-quality flags: mono or near-mono (S/M below about -30 dB, so route to scenario F), a spectral cutoff near 16 kHz (upstream 128k MP3/AAC, i.e. double-lossy), a DRC stream, or a sample rate other than 44.1/48k. Warn and continue. Never downmix at ingestion, because the stereo router and S=(L-R)/2 reference need L/R. Only the transcriber-specific adapters (e.g. Basic Pitch) downmix.
 - Hint lookup: take artist and title from track/artists (Art Track) or title parsing. For local files use AcoustID/MusicBrainz. Query the Songsterr search JSON for tuning arrays and part names. Pass them as soft priors to the router (expected guitar-part count), to tuning and capo inference, and to fret assignment. Always let the audio override them, and record the prior's source in meta.json.
 - Evaluation of the ingestion stage itself: for 5–10 songs you own on CD, run lossless vs YouTube 251 vs YouTube 140 through the same SW plus transcriber path and compare note-F1 and role leakage. Also compare MV vs album versions. Expect the version and trim choice to matter more than codec choice. If the codec gap is under about 1 point of F1, drop the dual-stream option.
 - Legal and UX: state plainly in the README/CLI that YouTube's ToS prohibit downloading without authorisation. Make local files a first-class input and recommend purchased or CD lossless audio. Keep downloads, stems and tabs private (personal non-commercial use), and do not redistribute stems.

AREA: bass

[SUMMARY]
Nobody has published an electric-bass-to-tab benchmark on separated pop stems, so the choice of primary engine below is inferred from nearby evidence.

**What the evidence says:**
- **Best real-audio number on separated bass (FiloBass, ISMIR 2023).** Test material is jazz upright bass separated with Demucs, scored by onset only at 50 ms. Note F1: CREPE Notes (F0 + segmentation) 72.9, Basic Pitch 62.7 (precision only 51.4, so it adds many false notes), Melodyne (commercial) 78.95 with no manual correction.
- **MuScriptor** (the strongest mixture-trained transcriber in the prior research) has `electric_bass` and `acoustic_bass` classes and a `--instruments` restriction. It publishes no per-instrument or bass F1. Off the shelf it scored only 0.457 onset+pitch F1 on isolated Slakh stems (Harmonica paper), so its bass quality must be measured, not assumed.
- **YourMT3+** reaches 93.2 bass onset F1 on synthetic Slakh and trains on real IDMT-SMT-Bass. It also found that Slakh bass labels sit an octave too high, that the pretrained MT3 outputs bass an octave high, and that commercial pop shows large octave errors. Octave errors are therefore the main failure mode. Abeßer's bass study shows the same thing: 0.701 exact-pitch accuracy versus 0.82 when octave errors are ignored.
- **Classic bass-specific systems** (Abeßer, TASLP 2017) reach note F 0.901 on solo DI bass tuned to the same instrument, which is an upper bound. They estimate string, plucking style and expression style. On realistic bass lines, even with correct notes given, accuracy is only 75.2% for string, 63.6% for plucking style and 44.2% for expression style. Slap vs non-slap separates cleanly; slap-thumb vs slap-pop does not; dead notes are confused with other expression styles.
- **Pitch-range traps for low B and drop tunings.** B0 = 30.87 Hz, E1 = 41.2 Hz.
  - CREPE and RMVPE: lowest bin ≈31.7 Hz.
  - torchcrepe: default fmin is 50 Hz, which silently drops E1 through about G1.
  - SwiftF0: floor is 46.875 Hz.
  - FCPE: marks anything under f0_min (example value 32.70 Hz) as unvoiced.
  - Safe: PESTO (CQT from 27.5 Hz) and Basic Pitch (27.5 Hz base, 88 semitones).
- **Tab stage.**
  - The recent tab models (TART, Fretting-Transformer) are guitar-only. The only bass-tab model (Anoufa/D'Hooge, AIMC 2025) generates new bass parts from a rhythm guitar track rather than transcribing audio.
  - Bass is mostly one note at a time, so an exact Viterbi/DP fingering search with a hand-position cost is the practical choice. AutoBassTab used this, penalising finger movement, open strings and high frets.
  - MuScriptor's own tab is only MuseScore's automatic staff conversion, not learned fingering.

**Recommendation (inferred):**
- **Primary:** MuScriptor-medium on the bass stem with `--instruments electric_bass`. Correct each note's pitch and octave with a PESTO F0 track (torchcrepe 'full' with fmin=30 and Viterbi as a second opinion). Low-confidence F0 with a strong onset marks a dead/ghost note; the F0 slope gives slides and bends. Then detect the tuning and run a Viterbi fingering search.
- **Fallback, and a second vote in an ensemble:** PESTO/torchcrepe followed by CREPE Notes segmentation. YourMT3+ is an optional third vote.
- **Optional paid, with a human in the loop:** Melodyne.

Validate on FiloBass, IDMT-SMT-Bass-Single-Track (has string/fret labels) and a few of the user's own songs with trusted tabs before locking in the primary.

[VERIFIED TAKEAWAYS]
 - Octave error is confirmed as the dominant bass failure mode. The YourMT3+ chroma gap on RWC-Pop, MT3's octave-high bass and Abeßer's RPA/RCA gap all show it, so a per-note F0 octave check is justified.
 - No published bass-specific F1 exists for MuScriptor. Electric bass is 42.8% of its real training tracks, not 24%. Pick the primary engine by measuring on FiloBass, IDMT-SMT-Bass-Single-Track and the user's own songs.
 - Every FiloBass number is confirmed (CREPE Notes 72.89, Basic Pitch 62.73 with precision 51.4, Melodyne 78.95), but Melodyne's lead is inflated because the reference was built from Melodyne output.
 - F0 floors are confirmed: CREPE/RMVPE bin 0 = 31.7 Hz, PENN 31 Hz, FCPE 32.70 Hz, SwiftF0 46.875 Hz, PESTO VQT and Basic Pitch 27.5 Hz. Only SwiftF0 fails on standard E1. FCPE, RMVPE, CREPE and PENN miss only 5-string low B.
 - torchcrepe must be called with fmin≥31.7 Hz (e.g. 32). fmin=30 as written in the research breaks decoding completely. CREPE Notes' torchcrepe backend is hard-wired to 50 Hz.
 - Abeßer's upper bounds on clean solo bass are confirmed: note F 90.1 when tuned to the same instrument, and even with ground-truth notes, string 75.2%, plucking style 63.6%, expression style 44.2%. Tab fingering should come from a DP/Viterbi playability cost, not from audio string cues.
 - No open audio-to-bass-tab model exists. TART and Fretting-Transformer are guitar-only, the AIMC 2025 bass model is generative, and MuScriptor's tab is MuseScore's automatic retyping (MuseScore 4 required). A custom DP fingering stage is justified.
 - Licences for personal use are all fine: MuScriptor weights CC BY-NC 4.0 (HF login required); YourMT3 weights Apache-2.0 on HF, code GPL-3.0; PESTO LGPLv3; CREPE Notes GPL-3.0; Basic Pitch Apache-2.0; PyGuitarPro LGPL-3.0; alphaTab MPL-2.0; IDMT sets CC BY-NC-ND; FiloBass CC BY 4.0.
 - The paid options that matter are Melodyne Assistant or higher (Essential has no MIDI export), BandLab membership for Harmonica, and Songsterr Plus. Songsterr already covers the exact YouTube → guitar plus bass tab use case and is the benchmark to beat.

AREA: tuning-fret-technique

[SUMMARY]
TUNING AND CAPO. Tuning estimation has three separate parts, and no published tool does all of them.
(a) Fractional reference offset (A=440 vs a detuned record). This is solved: librosa.estimate_tuning returns [-0.5, 0.5) semitone and Essentia TuningFrequency returns -35..+65 cents. Neither can tell E standard from Eb standard, because a whole-semitone detune looks like a key change.
(b) Integer downtune plus string interval profile. DadaGP's own tokenizer already splits tuning this way. It supports only the interval profiles g6_standard, g6_drop, g7_standard and g7_drop (bass: b4/b5/b6 standard and b4 drop) and stores the uniform downtune as a separate number. So Eb standard, D standard, C standard and B standard are all "standard shifted down". Drop D, Drop C# and Drop C are all "drop shifted down".
(c) Capo. Hulme (DLfM 2024) notes that a capo raises the lowest playable pitch, that tunings do not always follow A440, and that a tuning keeps its interval profile when every string is shifted by the same amount. Capo and "tuned up" therefore cannot be told apart from pitch alone; only playing conventions (open chord shapes, open-string riffs) break the tie.
The only audio tuning classifiers found are small: Hulme's CNN (acoustic, Joni Mitchell-centred) and a 2023 Rochester student project (260 clips, CREPE lowest-note gating plus OpenL3 plus SVM). Drop D, Open D and D standard were its worst classes, and CREPE made octave errors on polyphonic input. Recommendation: after transcription, decide tuning and capo symbolically as a hypothesis search. Enumerate interval profile × downtune × capo and score each by infeasible notes (below the lowest open string), DP playability cost and open-string use, with a prior over common tunings. Do not train an audio tuning classifier.

STRING/FRET ASSIGNMENT. Learned MIDI-to-tab arrangers now beat commercial software.
- Fretting-Transformer (ICMC 2025): a halved T5 (d_model 128, 3 layers). Tab accuracy is 81.58% on DadaGP vs 76.58% for Guitar Pro, and 72.19% vs 56.03% on Leduc. It takes CAPO and TUNING conditioning tokens covering standard, half-step down, full-step down and drop D, with capo up to 7. One co-author is from Klangio (the company behind Guitar2Tabs). The paper gives no code or weights link.
- Hsu et al. (arXiv 2607.26440, Jul 2026) add pitch-validity constrained decoding: 77.10% vs 71.78% for their Fretting-Transformer re-implementation on DadaGP. Training code is in MusicGuitarTab/GuitarTab (no weights, no license file).
- TART stage 3 is audio-conditioned (capo 0-7 plus 4 tunings), reaching 71.8% string-fret F1. It has no public code.
- tuttut (MIT) is a ready HMM/Viterbi arranger for any tuning and any number of strings.
- Audio-informed string classification works only on isolated or DI notes: Abeßer 2012 F=.90 guitar / .93 bass, Kehling 2014 82%, Fretiq 2026 87.8% free-play. None is shown to work on separated band stems. Use it at most as a weak tiebreaker.

TECHNIQUES. TART's 9-class technique classifier reports 95.9% macro F1 (vibrato is lowest at 89.4%). It was trained and tested on isolated technique datasets, and no code is available. The strongest evidence for band mixes is Chen, Su and Yang (ISMIR 2015). They pick candidates from the F0 contour, then refine them with an SVM. On unaccompanied solos: bend F 87.7%, vibrato 84.0%, slide 57.7%, average 74%. On accompanied studio mixes, bend F is 67.3%, and contour rules alone beat the SVM there.
Basic Pitch's per-note bends are argmax offsets in 1/3-semitone units at 86 frames/s, weighted by a Gaussian (std 5 bins). That is enough for half-step and full-step bends and slides, but coarse for vibrato. CREPE gives 20-cent bins at 10 ms and is MIT-licensed.
Palm mute, harmonics, pinch harmonics and dead notes need a timbre classifier. Trainable open data exists: EG-IPT (CC BY 4.0, 28.4 h, 19 techniques, DI plus mics), Guitar-TECHS (CC BY 4.0), IDMT-SMT-Guitar (CC BY-NC-ND 4.0) and GOAT (by request). DadaGP's note-effect tokens (bend, vibrato, slide, hammer, palm_mute, harmonic, dead, ghost_note, let_ring, ...) support an expression-aware symbolic model.

FEASIBLE NOW:
- cents offset → pitch-correct → transcribe;
- rule-based tuning/capo hypothesis search on the transcribed notes;
- tuttut or your own Viterbi arranger, run in a base tuning after transposing by the detected downtune;
- f0-rule detection of bends, releases, pre-bends, vibrato, slides and hammer-ons/pull-offs;

[RECOMMENDATIONS]
 - TUNING STAGE T1 (fine offset, do it first): run librosa.estimate_tuning (resolution 0.01) on the harmonic part of the full mix over the whole song. If |offset| is above about 15 cents (threshold is a design choice to calibrate), pitch-shift the audio by -offset before separation or transcription so the transcriber's semitone bins line up. Record A = 440·2^(c/1200) in the tab header. This only covers the part below a semitone.
 - TUNING STAGE T2 (symbolic hypothesis search on transcribed notes, per stem): enumerate hypotheses. Guitar: interval profile {6-std, 6-drop, 7-std, 7-drop} × downtune {0..-5 semitones} × capo {0..7} (capo usually only when downtune is 0). Bass: {4-std, 4-drop, 5-std} × downtune. Score each by (a) the share of confident notes below the lowest open string, measured with a low percentile rather than the minimum, (b) DP playability cost from tuttut or your own Viterbi, (c) open-string and fret-0 riff usage (drop-tuned riffs sit on 0-0-0 power chords), and (d) a prior (E std > Eb std > Drop D > D std > Drop C# / Drop C > C std; 7-string B only if notes fall below D2). Show the top 2 with a margin and let the user override. Tuning is chosen per guitar part, since guitarists in one band may use different tunings.
 - Guard T2 against false low notes. Before taking lowest-note statistics, drop guitar-stem notes below E2 that coincide in time with bass-stem notes of the same pitch class (bass bleed), and notes with only a single octave-below-partner (octave errors; CREPE and Basic Pitch both make these on polyphony). Otherwise E-standard songs will be misread as drop or 7-string.
 - Use interval-profile equivalence to cover every tuning with one arranger. Transpose the notes up by the detected downtune, run the arranger in its base tuning (E standard or drop D; 7-string handled by DP), then label the tab with the real tuning. Frets are identical. Learned arrangers trained only on {standard, half-step down, full-step down, drop D} then work for Drop C, C standard and similar tunings. Treat capo the same way, with a hard 'no fret below capo' rule.
 - STRING/FRET, phase 1 (now): tuttut or a custom Viterbi arranger with costs for hand span (at most 4-5 frets), position shifts, open-string bonus, same-string legato continuity for detected HO/PO and slides, and chord-shape templates for rhythm parts. Emit GP5 via PyGuitarPro and render with alphaTab.
 - STRING/FRET, phase 2 (after DadaGP access is granted): train the small T5 arranger from MusicGuitarTab/GuitarTab with pitch-validity constrained decoding, plus profile, downtune and capo tokens. Train on degraded input (randomly drop 20-30% of notes, add octave errors, jitter onsets), because at inference it sees transcriber output, not clean MIDI. Evaluate tab accuracy on held-out DadaGP and TDR on GuitarSet. Keep the DP as a fallback and for 7-string and bass.
 - Do not build audio-based string classification for band stems yet. All published accuracies (Abeßer .90/.93, Kehling 82%, Fretiq 87.8%) are on isolated or DI notes, and humans score .16-.26. If added later, use it only as a soft prior inside the DP, with TART- or Noise2Fret-style training on reamped GOAT/EG-IPT audio.
 - TECHNIQUES, tier 1 (rule-based on f0, now): for lead or monophonic segments, run torchcrepe (Viterbi) on the lead stem; fall back to Basic Pitch per-note bends. Rules to calibrate on GOAT/Guitar-TECHS (thresholds are unverified starting points): bend = rise of at least about 80 cents after the onset with no new onset, quantized to ½, full or 1½ steps; release = return toward the base pitch; pre-bend = note starts high and falls; vibrato = 4-8 Hz oscillation of at least about 20 cents depth (needs CREPE resolution); slide = continuous glide over at least 2 semitones joining two notes with a weak onset; hammer-on/pull-off = pitch change with no spectral-flux onset peak, within 1-4 frets on the same string. Chen/Su/Yang show contour rules alone reach bend F 67% in real mixes and beat a classifier trained on clean data.
 - TECHNIQUES, tier 2 (trained classifier, later): palm mute, natural and pinch harmonics, dead or ghost notes and percussive hits need timbre. Train a small per-onset CNN on EG-IPT (CC BY 4.0, includes DI for reamping), Guitar-TECHS and GOAT. Augment with your separator's artifacts: mix with other stems, run BS-RoFormer, then train on the output. Do not rely on TART's 95.9% figure; it was measured on isolated data and no code exists. Cheap heuristics meanwhile: harmonic = pitch far above the plausible fret range for the string or chord context; dead note = guitar-stem onset with no stable pitch (write 'x'); palm-mute candidate = short decay with a low spectral centroid in rhythm parts; let ring = assigned notes on different strings that overlap in time.
 - Bass: tuning search over 4-std, 4-drop and 5-std (B0 is inside Basic Pitch's range, whose lowest bin is 27.5 Hz). Techniques for v1: slides, HO/PO, ghost notes and vibrato from the same f0 rules. Defer slap/pop to a later classifier.
 - UI and evaluation: show detected tuning, capo and cents offset with confidence at the top of each tab, editable, with re-arrangement on change. Mark technique flags per note with confidence so they can be removed with one click. Measure tuning accuracy on 20-30 of your own songs with known tunings (Songsterr and official tabs, checked by hand, not scraped). Measure technique F1 per class on GOAT and Guitar-TECHS, and on stems separated from your own mixes of those DI tracks.

[VERIFIED TAKEAWAYS]
 - No released weights exist for any learned MIDI-to-tab arranger checked here (Fretting-Transformer, Hsu/GuitarTab, MIDI-to-Tab, TART, open-fret). The day-1 arranger must be DP/Viterbi (tuttut or custom). Any learned arranger has to be trained by the user.
 - Fretting-Transformer's paper-level results are verified: 81.58% DadaGP vs Guitar Pro 76.58%; tuning/capo-conditioned model 79.89%. Its conditioning covers only standard, half-step down, full-step down and drop D, with capo 0-7. The interval-profile-plus-transpose trick is needed for other tunings.
 - Whole-semitone detune cannot come from reference-pitch estimators: librosa gives [-0.5, 0.5) of a semitone and Essentia -35..+65 cents. Symbolic hypothesis search after transcription is the justified approach. Published audio tuning classifiers are weak: 73.9% on 5 classes (Hulme) and 71.7-74.2% on 7 classes (Rochester), with D-family tunings confused and CREPE octave errors on polyphony.
 - Technique detection in real mixes: the only mix-level evidence is Chen/Su/Yang 2015, bend F 67.3% from contour rules alone, where an SVM trained on clean data made things worse. TART's 95.9% macro F1 (vibrato 89.4%) is on isolated technique samples only and has no code. Plan f0-rule detection first and treat classifier numbers from isolated data as upper bounds.
 - Audio-based string classification is proven only on isolated or DI notes: Abeßer .90 guitar / .93 bass, Kehling 82%, Fretiq 87.8% single-player. The '.26/.16 human listener' figure is unsupported and should be removed.
 - Basic Pitch bends are argmax-quantized to 1/3 semitone at about 86 fps, with a Gaussian (std 5 bins) window that down-weights wide bends. Use torchcrepe (MIT, PyTorch, CUDA on sm_75) for vibrato and bend depth on lead lines.
 - Open training data licenses: EG-IPT CC BY 4.0 (ipt_recognition code is CC BY-NC 4.0); Guitar-TECHS CC BY 4.0 (standard tuning only); GOAT CC BY 4.0 but access by request; IDMT-SMT-Guitar CC BY-NC-ND 4.0; SynthTab CC BY-NC 4.0 (about 2 TB). All are fine for personal non-commercial use.

AREA: notation-output

[SUMMARY]
RHYTHM. Use Beat This! (CPJKU, ISMIR 2024, MIT, PyPI beat-this 1.1.0 released 2026-04-14) as the rhythm backbone. It is pure PyTorch, and madmom is needed only for the optional --dbn flag. It outputs beat and downbeat times. It does not output tempo or time signature, so derive both: tempo from inter-beat intervals, meter from how many beats fall between downbeats. On GTZAN it beats the previous state of the art on F1 (beats 89.1 vs 88.7, downbeats 78.3 vs 75.6) but is worse on continuity (CMLt). It drops the DBN step, so it does not force a fixed tempo or meter, which suits tempo drift and meter changes. madmom has had no PyPI release since 0.16.1 (2018) and fails to import on Python 3.10; it works only from GitHub (0.17.dev0), and its models are CC BY-NC-SA. All-In-One (allin1) is the only open tool that also labels song sections, but it is fragile on native Windows. Its last PyPI release was 2023-10, it needs NATTEN (NATTEN's docs say its Windows builds are experimental and not regularly tested) and madmom from git, and it has an open NATTEN-incompatibility issue. Use it only via WSL, or skip it. Newer 2026 papers (masked-diffusion beat tracking at ISMIR 2026, the "SMC blind spot" failure analysis) show the remaining errors are octave (half/double tempo) and continuity errors. They are not drop-in tools.

QUANTIZATION. The best published result comes from Klangio/KIT (Wachter, Murgul, Heizmann, arXiv 2604.22290, April 2026). It is a transformer that takes beat annotations and quantizes onto 12 sub-beats per beat, which covers straight notes and triplets down to 16th-note triplets. It reaches 97.3% onset F1 on ASAP and 92.1% onset F1 with a guitar-trained model (Leduc jazz guitar). Its MUSTER onset error rate is 12.30, against 15.55 for end-to-end PM2S, 22.58–25.02 for HMM+heuristics and 47.90 for MuseScore. No code or weights were mentioned. The open quantizers (MIDI2ScoreTransformer, PM2S) are trained on piano. MuseScore 4 dropped MuseScore 3's MIDI-import quantization panel, and the feature request is still open. So build our own beat-relative grid quantizer on the Beat This! grid, and detect swing or triplet feel from where off-beat onsets fall (swingogram-style swing-ratio estimation is the literature basis).

OUTPUT. Guitar Pro and alphaTex carry the full set of guitar techniques. PyGuitarPro 0.11 (2026-05-03, LGPL-3.0, Python 3.10 or later) reads and writes only GP3/4/5, but its note effects include palm mute, bends with curve points, slides, hammer-on, harmonics, let ring and vibrato, and each bar carries triplet feel and time signature. alphaTab (MPL-2.0; stable 1.8.4 released 2026-07-05, 1.9 in alpha) reads GP3–GP7+, MusicXML and alphaTex. It renders standard notation plus tab for multiple tracks in the browser, and renders SVG/PNG in Node.js. It exports .gp through Gp7Exporter (since 1.2.0) and alphaTex (since 1.7.0), but has no MusicXML export. Since 1.6 it syncs the score to external audio or video through sync points; alphaTex syntax is \sync BarIndex Occurence MillisecondOffset [RatioPosition], and a custom media handler covers players such as a YouTube embed. It plays either the external audio or its synthesizer, not both at once. MusicXML 4.0 has bend, slide, hammer-on/pull-off, string and fret elements but no palm-mute element (palm mute becomes a text-plus-bracket direction). MuseScore 4's command line (-o, -j) converts to PDF, MusicXML and MIDI but cannot write Guitar Pro. MuseScore imports GP files, including .gp since 3.5.

BASELINES. Songsterr AI takes a YouTube link or an upload. It offers configurable rhythm guitar, lead guitar, bass, drums and other tracks, and detects time signature, tempo, pickup bar and triplet feel automatically. It produces a draft to edit in Songsterr's editor. Klangio Guitar2Tabs isolates "the guitar or bass part" (YouTube or upload input; exports PDF, quantized and unquantized MIDI, MusicXML and GP). An independent MusicRadar review (updated 2026-07-10) found it good on solo acoustic guitar but weak on full mixes, swing and expressive timing, techniques such as harmonics, and open tunings. Moises detects chords only and gives no fret-level tabs. RipX gives note-level audio-to-MIDI and guitar chord detection, with no tab export listed. The 2026 generators Songscription, Tabtify and audio2guitar publish no accuracy benchmarks, and their own comparison blogs admit full mixes need cleanup. So "beat the baselines" has to be measured on the user's own evaluation set.

[RECOMMENDATIONS]
 - Rhythm backbone: run Beat This! on the FULL MIX (drums and bass carry the pulse), not on the guitar stems. Build a tempo map from inter-beat intervals and bar lines from downbeats. Infer meter per section as the mode of beats-per-bar. Treat the first downbeat as the pickup (anacrusis) boundary. Add a half/double-tempo check, for example comparing the note density of the bass/guitar onsets against the beat rate, because octave errors are the dominant remaining failure. Optionally run madmom's DBN (git build) as a second hypothesis and prefer the one with fewer onset-to-grid residuals.
 - Skip All-In-One on native Windows (NATTEN). If section labels (verse/chorus) are wanted for tab markers, run allin1 inside WSL2 as an optional stage. Otherwise start without it.
 - Quantizer (build our own; no open guitar quantizer exists): reuse Klangio's published grid idea of 12 sub-beats per beat on the Beat This! grid, which covers 16ths and triplets. For each beat, choose a binary (4-subdivision) or ternary (3/6-subdivision) grid by Viterbi, minimising onset error with a penalty for switching. Snap onsets, then derive durations from the next onset or offset, and emit ties across beats and bars. Evaluate with a MUSTER-style onset error rate and aim for well under MuseScore-import levels.
 - Swing/triplet feel: measure where eighth-note off-beat onsets fall within each beat, a simplified swingogram. If they cluster near 2/3 of the beat for a section, set GP/alphaTex tripletFeel (8th) and notate straight eighths, as Songsterr's 'triplet feel' option does. Otherwise quantize literally.
 - Keep two timelines. The score gets a readable rounded tempo, with tempo changes only for sustained section-level changes. The per-bar audio times from Beat This! go out as alphaTex '\sync BarIndex 0 MillisecondOffset' points, so the alphaTab cursor follows the original recording despite drift. Keep the unquantized performance MIDI as well, as Klangio does, for debugging and A/B.
 - Canonical internal model: one JSON (tracks for guitar parts and bass, then bars, beats and notes with string/fret/technique flags and per-note confidence). Emitters in priority order: (1) alphaTex, the primary format for the web viewer; (2) .gp via alphaTab Gp7Exporter in a small Node 24 script (ScoreLoader.loadAlphaTex then Gp7Exporter); (3) .gp5 via PyGuitarPro 0.11 for compatibility; (4) MIDI via pretty_midi, one track per part, quantized and performance versions; (5) PDF/MusicXML via the MuseScore 4 CLI from the .gp/.gp5. Treat MusicXML as secondary because it has no palm-mute element and MIDI has no string/fret.
 - Viewer: a local web page using alphaTab 1.8.x with multiple tracks (Guitar 1/2/..., Bass), standard notation plus tab, track mute/solo, and EnabledExternalMedia bound to the local audio file, the separated stems, or a YouTube embed through IExternalMediaHandler. alphaTab cannot play synth and backing audio together, so for 'hear my tab over the song' run a separate WebAudio mix of the stems alongside alphaTab playback, or offer an A/B toggle.
 - Python 3.10 venv pins: beat-this 1.1.0, PyGuitarPro 0.11, pretty_midi, music21<10 (10.x needs Python 3.11 or later). Add madmom only from git, and only if the DBN hypothesis is used.
 - Baseline protocol for claiming 'better than products': pick 5–10 songs the user actually covers that have trusted reference tabs (official GP or high-rated Songsterr/akbobada), and run the same audio through Songsterr AI (rhythm/lead/bass tracks) and Klangio Guitar2Tabs (a 20 s demo or one paid month), optionally Songscription or Tabtify. Score each guitar part and the bass on note onset F1, string/fret agreement, role leakage between guitar tracks, bar/meter correctness and quantization onset error, and record 'minutes of editing to playable' as the human metric. Moises and RipX are not tab baselines.
 - Legal/UX: accept local audio files as the primary input. Keep YouTube fetching as an optional, user-initiated step (a separate yt-dlp install) and flag the YouTube ToS in the UI, even though Songsterr and Klangio accept YouTube links.

[VERIFIED TAKEAWAYS]
 - Beat This! (MIT, beat-this 1.1.0, 2026-04-14) is a sound rhythm backbone. It gives beats and downbeats only, has SOTA F1 but lower continuity than DBN systems, and was trained on 18 datasets including GuitarSet. Tempo, meter and half/double-tempo checks must be derived. Declare torchaudio plus soundfile and feed WAV on Windows.
 - madmom stays at PyPI 0.16.1 (2018) and is broken on Python 3.10 from PyPI. Use it only from git, only for the optional DBN, and remember its models are CC BY-NC-SA, which is fine for personal use.
 - allin1 is not viable on native Windows: NATTEN's Windows builds are experimental, issue #30 (API break at NATTEN 0.17.5) is still open, and the last release was 2023-10. Skip it, run it under WSL with an old pinned NATTEN, or evaluate SongFormer instead.
 - Rhythm quantization: build a beat-relative grid quantizer ourselves. Klangio's 12-sub-beat (32nd-triplet) grid is the best published design, but its 92.1% guitar onset F1 used ground-truth beats and score-derived MIDI, so expect lower numbers in a real audio pipeline. Open quantizers are piano-only, and MIDI2ScoreTransformer needs Python 3.11 and has no license.
 - Output stack: alphaTex, then alphaTab (MPL-2.0, 1.8.4) for .gp export via Gp7Exporter and rendering, plus PyGuitarPro 0.11 (LGPL-3.0, GP3–5) for .gp5, pretty_midi for MIDI, and the MuseScore CLI for PDF/MusicXML only (it cannot write GP). In alphaTex, triplet feel is '\tf', not '\tripletFeel'.
 - alphaTab sync points ('\sync bar occurrence ms ratio?') and EnabledExternalMedia can drive a local audio file or a YouTube embed. To hear the tab over the song, pre-render the synth with the Audio Export API and mix it with the stems.
 - MusicXML has no palm-mute technical element but supports <mute>palm</mute> for playback. GP/alphaTex remain the canonical technique carriers.
 - No commercial product publishes tab accuracy. Songsterr AI (50/month on Plus, rhythm/lead track options) and Klangio Guitar2Tabs (one guitar or bass part, GP/MusicXML/MIDI/PDF; API available) are the real baselines. Moises and RipX are not tab baselines. The MusicRadar review tested Klangio Transcription Studio, not Guitar2Tabs, and found solo open-tuned blues guitar a failure, so the research's 'good on solo acoustic' claim is wrong.
 - The design needs a human editing step (TuxGuitar, Guitar Pro 8 or the Songsterr editor), because alphaTab only views and plays. 'Minutes of editing to playable' is the right human metric; use mir_eval for the automatic ones.

[SUMMARY]
(1) MuScriptor (github.com/muscriptor/muscriptor, v0.3.0, Kyutai x Mirelo, arXiv 2607.08168). The code is MIT and the weights are CC BY-NC 4.0. The weights are gated: before first use the user has to accept the licence on Hugging Face and log in or set HF_TOKEN himself. On Windows the GPU install is `uvx --torch-backend=cu128 muscriptor ...`, or `pip install muscriptor` into a venv (Python >=3.10). PyTorch cu128 wheels include sm_75, so the RTX 2060 is supported.
- Models: decoder-only transformers in three sizes, small 103M, medium 307M (default) and large 1.4B. The checkpoints are fp32 safetensors of 412 MB, 1.23 GB and 5.47 GB. On CUDA the default keeps fp32 weights and runs fp16 autocast. `--dtype float16` casts the transformer to fp16, while the mel and class conditioners stay fp32.
- Input: any audio file (wav, mp3, flac). It is downmixed to mono, resampled to 16 kHz and cut into 5.0 s chunks with no length limit. Chunks are decoded in order. 'Prelude forcing' re-feeds the notes still sounding from the previous chunk so that instruments do not flip at chunk boundaries.
- Instrument classes: 36 MT3_FULL_PLUS groups, including acoustic_guitar, clean_electric_guitar, distorted_electric_guitar, acoustic_bass and electric_bass. There is one output track per group, so two guitars of the same class always merge into one track. The tokenizer also cannot hold two overlapping notes with the same pitch and the same instrument. Keeping such notes in the test set drops onset F1 from 60.4 to 51.8, which means unison-doubled guitars collapse into one note stream.
- Conditioning: you can condition on the set of instruments present in the whole track. In the paper this raised onset F1 from 51.6 to 53.2 and multi F1 from 38.7 to 40.5, and it stabilises the instrument labels across segments. The CLI `--instruments` flag does two things: it applies that conditioning and it also hard-masks every instrument not in the list.
- Output: midi, json or jsonl, or `--format sheets`. Sheets needs MuseScore 4 or newer and produces quantized MIDI, MusicXML, a full score PDF and one PDF per instrument, plus a tab PDF for fretted instruments. The tab comes from MuseScore's automatic tab-staff conversion. Tempo and downbeats come from beat-this, and results are best with a steady tempo.
- Accuracy: on the paper's real-music test set the 1.3B model scores onset F1 60.4 and multi F1 48.2, against 32.5 and 21.2 for YourMT3+. The paper gives no per-instrument guitar or bass F1. In the paper's scaling ablation (real data only, no RL), medium (300M) reaches 39.7 multi F1 and 1.3B reaches 40.5, so medium is close to large.
- Third-party numbers (Harmonica paper): on an RTX 4090, released MuScriptor-medium runs at 17.0x real time and YourMT3+ at 45.6x. MuScriptor-medium scores OnP F1 0.710 on GOAT, 0.789 on EGDB and 0.808 on GuitarSet. The YourMT3+ row in that table is a model the Harmonica authors retrained, not the public checkpoint.
- Not yet measured on the 2060 (estimates): VRAM use and speed. Medium should fit easily. Large should fit only with --dtype float16, at about 2.7 GB of weights.

YourMT3+:
- Code is on GitHub under GPL-3.0. There is no pip package. The runnable code and checkpoints sit in the Hugging Face Space mimbres/YourMT3, whose card says apache-2.0, so the licensing is inconsistent (either is fine for personal use).
- The Space pins old dependencies: transformers==4.45.1, numpy==1.26.4, lightning>=2.2.1, and torch from the cu113 index. It needs its own venv.
- Recommended checkpoint: 'YPTF.MoE+Multi (noPS)', run with FP16 inference. Input is mono 16 kHz in 32767-sample (about 2.05 s) segments, batch size 8. Output is one MIDI file.
- It uses the same three-way guitar taxonomy as MuScriptor, so same-class guitars merge in the same way. Use it only as a faster second opinion or an ensemble member.

(2) Guitar-part counting and tracking. My searches found no published method that counts or 'diarizes' guitar parts, so this has to be built. Four existing things can be reused:
- Clustering-based multi-instrument transcription. Tanaka et al. (ISMIR 2020) and Li & Zhu (TISMIR 2026) both need the number of parts given in advance. Tanaka ran with N=3, reached guitar frame F about 40 on Slakh, and had to match clusters to instrument labels by hand.
- Constrained clustering from multi-pitch streaming (Duan, Han & Pardo). It uses must-link between pitches close in time and frequency, cannot-link between simultaneous pitches, and a timbre-consistency objective. It needs K given and assumes monophonic sources.
- Diarization templates from other audio work. Singer diarization (Suda et al. 2022) separates the voices, embeds short segments and clusters them. Spatio-spectral diarization (Interspeech 2025) segments by spatial cues, then clusters by embedding, and needs no known count. Carnatic percussion diarization decides where sources overlap before separating.
- Off-the-shelf features:
  - activity: PANNs sound-event detection on AudioSet classes (Electric/Acoustic/Bass guitar, Distortion, Strum, Guitar amplifier), and the MERT solo detector from the earlier research;
  - timbre: CLAP 'style' embeddings, which align best with human timbre-similarity ratings (Tian et al. 2025). Banquet/PaSST query embeddings are explicitly insensitive to fine timbre differences, so they cannot tell Guitar 1 from Guitar 2;
  - a count prior from DadaGP, whose 26,181 GuitarPro songs mostly have four parts, usually two guitars plus bass and drums, with at most 3 distorted and 2 clean guitars.

What must be built: a window-level (2–4 bar, from the beat-this grid) 'guitar-part diarizer' with these steps:
- Collect observations per window from every route: stereo routes, MVSEP lead/rhythm stems, and the MuScriptor class tracks.
- Give each observation features: activity, pan position, CLAP-style timbre, role features (polyphony, register, note density, repetition) and the guitar class token.
- Cluster them with constraints: cannot-link for simultaneous observations in the same window; must-link for continuity across adjacent windows and for repeated sections.
- Choose K between 1 and 4 by silhouette/eigengap plus the DadaGP prior, and let the user override it.
- Merge double-tracked copies into one part when their transcriptions match note for note.
- Smooth labels with Viterbi or an HMM switch penalty, and use Hungarian matching across repeated sections.
- Evaluate with part-count accuracy, a window-level part-diarization error, and note-level part-assignment accuracy.

 - Step 1 (install): Create a project venv with `py -3.10`, install the torch cu128 wheel (it includes sm_75), then `pip install muscriptor`. The user must accept the CC BY-NC licence on the Hugging Face model page and run `hf auth login` himself. Don't use --format sheets as the product. Consume --format json or midi (Python API: TranscriptionModel.load_model / transcribe) and do fret assignment in your own tab stage, because MuseScore's automatic tab is not learned fingering.
 - Step 2 (benchmark on the 2060 before designing around sizes): time medium at its default (fp32 weights + fp16 autocast) and large with --dtype float16 on 3 songs, and log torch.cuda.max_memory_allocated. Avoid bfloat16 on Turing. The paper's ablation shows only 0.8 multi-F1 between 300M and 1.3B, so default to medium and treat large as an optional quality pass.
 - Step 3 (conditioning discipline): the CLI --instruments flag also hard-masks every instrument not listed. On the full mix, pass the song's complete lineup (e.g. distorted_electric_guitar, clean_electric_guitar, electric_bass, drums, vocals if applicable, piano if present), otherwise notes from keys or synths get forced into guitar classes. On a guitar-only stem, pass only the guitar classes. Run MuScriptor on several inputs per song (full mix, 'other' residual, guitar stem, L / R / centre / S routes) and keep every output as a candidate observation.
 - Step 4: keep YourMT3+ as an optional ensemble member in a separate venv, because its old dependency pins would conflict with MuScriptor's numpy>=2. Use the noPS checkpoint. Its value is speed and a second vote, not accuracy.
 - Step 5 (build the guitar-part diarizer; nothing off-the-shelf exists): (a) set up bar-aligned 2-4 bar windows from beat_this, with section labels from all-in-one. (b) For every route and window, create an observation with these features: activity (MuScriptor note count per guitar class, RMS, PANNs guitar/strum/distortion probabilities), stereo position (coherence-weighted pan histogram peak), timbre (CLAP style embedding of the masked audio), role (polyphony, register, note density, chord ratio, repetition score) and class token (clean, distorted or acoustic). (c) Cluster with constraints: cannot-link observations active in the same window on different routes; must-link adjacent windows whose pan, timbre and role are continuous, and repeated sections matched by self-similarity. (d) Choose K in 1..4 by silhouette or eigengap, with a DadaGP-style prior favouring 2, and always let the user override K.
 - Step 6 (count parts musically, not acoustically): merge two observations into one part when their transcriptions match (note F1 above a tuned threshold, e.g. about 0.8, while being panned apart). That is a double-tracked rhythm part, not two guitars. MuScriptor's same-pitch/same-class collapse already helps here. Treat lead doubling in harmony (thirds or fifths) as two parts unless the user says otherwise.
 - Step 7 (identity consistency): smooth the per-window part labels with Viterbi or an HMM switch penalty. Use Hungarian matching of cluster labels between repeats of the same section. Name the parts deterministically, e.g. Guitar 1 = the part active in the most windows (usually rhythm) and Guitar 2 = the part holding the solo windows from the MERT solo detector. Flag low-confidence windows in the tab output instead of hiding them.
 - Step 8 (evaluation): build 10-20 reference songs with known parts (your own recorded covers, official multitracks, or GuitarPro tabs aligned to the audio). Report: part-count accuracy per song, a window-level part-diarization error (DER-style), note-level part-assignment accuracy after Hungarian matching (as Tanaka et al. did), and note F1 per part. Do not rely on SDR.
 - Do not plan on Banquet/PaSST query embeddings or MuScriptor/YourMT3+ class tokens to split two guitars with the same tone. Neither can do it; the published evidence is explicit. The discriminating signals for same-tone parts are stereo position, role and repetition, and a user hint.

[VERIFIED TAKEAWAYS]
 - MuScriptor facts hold up against code and the HF API: v0.3.0, MIT code and gated CC BY-NC 4.0 weights; 103M/307M/1.4B sizes with fp32 files of 412 MB/1.23 GB/5.47 GB; mono 16 kHz with 5 s chunks and no length limit; prelude forcing with batch size 1; `--instruments` both conditions and hard-masks; one track per MT3_FULL_PLUS group, so same-class guitars merge; same-pitch/same-instrument overlaps cannot be represented; sheets/tab output needs MuseScore 4 and has no learned fingering.
 - The YourMT3+ baseline numbers were wrong. MuScriptor paper Table 1 has YourMT3+ at onset 32.52 / frame 45.54 / offset 17.79 / drums 41.4 / multi 21.9. MuScriptor's 60.4/73.3/49.0/50.2/48.2 is correct but measured on its own in-distribution test set. On RWC-C and RWC-R, YourMT3+ is equal or better on several metrics.
 - Medium is the right default on an RTX 2060. The scaling ablation shows 39.7 vs 40.5 multi F1 for 300M vs 1.3B, and Harmonica measured medium at 17x real time on a 4090. Large with --dtype float16 will not simply fit in 6 GB: the loader puts the fp32 model and the fp32 state_dict on the GPU before casting (about 11 GB peak), so it needs a CPU-side load patch.
 - Use a Python 3.12 venv with cu126 or cu130 torch. Both include sm_75. `--torch-backend=cu128` works but caps torch at 2.11.0, and Python 3.10 reaches EOL in October 2026. YourMT3+ needs its own venv (numpy==1.26.4 and transformers==4.45.1 conflict with MuScriptor's numpy>=2), and its torch must be pinned explicitly.
 - The instrument-conditioning gain (+1.6 onset, +1.8 multi F1) was measured with ground-truth instrument lists on a DReal-only model. Because the CLI flag also hard-masks, a wrong or incomplete lineup can force keyboard or synth notes into guitar tracks.
 - The literature citations for part counting and tracking check out: Tanaka 2020 (N fixed, manual label matching, guitar F about 40 in 3-instrument mixes), Li & Zhu TISMIR 2026 (K given), Duan/Han/Pardo (K given, monophonic sources), Suda 2022 (ArcFace + Cosacorr), Cord-Landwehr Interspeech 2025 (HDBSCAN, no count needed). None of them tracks multiple same-class guitars in rock mixes, so a custom diarizer is justified. GuitarDuets (ISMIR 2024) is the closest same-timbre separation work.
 - The timbre-embedding choice needs fixing. The best style embedding in Tian et al. 2025 comes from Microsoft CLAP 2023 (msclap, MIT, repo archived 2026-09-15), not LAION-CLAP. It was validated only on isolated tones up to 4.39 s, and MFCC stays competitive, so treat it as a candidate feature to benchmark, not a proven guitar-part discriminator.
 - Useful signals for same-tone guitar parts: stereo azimuth (ADRess-style), role (rhythm-guitar detection from Régnier et al. 2021), repetition, and a user K override. The DadaGP prior of about 2 guitars is real but biased toward rock/metal, and its 3-distorted/2-clean limit is a format cap, not a statistic.
 - Windows install traps: panns_inference downloads with wget (pre-download manually); all-in-one needs NATTEN built from source; the MuScriptor model card's IP-rights clause means the user must accept responsibility for transcribing copyrighted YouTube audio.
